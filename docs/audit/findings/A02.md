## What Works (Verified Strengths)

1. **Cryptographically Strong Password Hashing & Anti-Enumeration Timing (`better-auth@1.7.14`)**:
   - Verified in `node_modules/better-auth/dist/crypto/password.mjs:1–18` and `node_modules/@better-auth/utils/dist/password.mjs:4–25`: passwords are NFKC-normalized (`password.normalize("NFKC")`), salted with 16 CSPRNG bytes (`getRandomValues(new Uint8Array(16))`), hashed with `@noble/hashes/scrypt.js` (`N = 16384`, `r = 16`, `p = 1`, `dkLen = 64`), and compared via constant-time `constantTimeEqual`.
   - On `POST /api/auth/sign-in/email` when an email does not exist (`node_modules/better-auth/dist/api/routes/sign-in.mjs:318–322`), Better Auth still executes `ctx.password.hash(body.password)` against a dummy password before returning generic `"Invalid email or password"` (`401`), mitigating timing-based user enumeration.
2. **Self-Service Role Escalation Blocked on `user.additionalFields`**:
   - `lib/auth.ts:41–54` configures `role` (`L42–47`) and `isActive` (`L48–53`) with `input: false`, preventing an authenticated `staff` session from passing `{ role: "super_admin" }` to Better Auth's built-in `POST /api/auth/update-user` endpoint.
3. **Defense-in-Depth Server-Side Guard on Admin Views & Layouts**:
   - Every active `/admin/*` view (`8` `page.tsx` files) **and** `app/admin/(dashboard)/layout.tsx:22` call `await requireAdmin()` (`lib/auth-guard.ts:19–40`) on the server. Even if `proxy.ts` is bypassed with a forged/expired cookie string, RSC rendering queries Neon PostgreSQL via `auth.api.getSession({ headers: reqHeaders })` (`lib/auth-guard.ts:9–11`; `session.cookieCache` is disabled, so `session JOIN user` runs on every request) and immediately checks `if (user.isActive === false)` (`L31`) and `if (user.role !== "super_admin" && user.role !== "staff")` (`L35`).
4. **Open-Redirect Protection on `/admin/login`**:
   - `app/admin/(auth)/login/page.tsx:26–30` computes `rawTarget = searchParams.get("callbackUrl") || searchParams.get("from") || "/admin"` and enforces `rawTarget.startsWith("/admin") && !rawTarget.startsWith("//")` before falling back to `"/admin"`, blocking external redirects (`https://evil.com`, `//evil.com`, `javascript:...`).
5. **Constant-Time Meta Webhook HMAC & Single-Use OAuth CSRF/PKCE Cookies**:
   - `app/api/webhooks/whatsapp/route.ts:19–25, 162–196` and `lib/whatsapp/webhook-signature.ts:18–77` enforce a `1 MB` raw-body cap (`413`), fail closed when `META_APP_SECRET` is missing, and verify `x-hub-signature-256` with `crypto.timingSafeEqual`.
   - `app/api/oauth/social/[provider]/route.ts:75–107` and `callback/route.ts:99–116` generate 32-byte `crypto.randomBytes` `state` + PKCE `codeVerifier` values in 15-minute `HttpOnly`, `SameSite=Lax` cookies and delete them immediately upon callback consumption.

### A02-001 — Unauthenticated Public Admin Self-Registration via `POST /api/auth/sign-up/email`
- Severity: P0
- Category: security
- Where: `lib/auth.ts:37–55`; `app/api/auth/[...all]/route.ts:4`; `lib/auth-client.ts:13`; `db/schema/auth.ts:24–25`; `lib/auth-guard.ts:31–39`; `app/actions/catalog.ts:876`; `db/seed.ts:26, 64`
- Brief claim contradicted (if any): §2.2 "Role-based staff management (`super_admin` and `staff`)"
- Evidence: `lib/auth.ts:37–39` configures `emailAndPassword: { enabled: true }` without `disableSignUp: true`, and `app/api/auth/[...all]/route.ts:4` mounts `export const { GET, POST } = toNextJsHandler(auth)` outside `proxy.ts` (`matcher: ["/admin/:path*"]`, `proxy.ts:45`). In `better-auth@1.7.14` (`node_modules/better-auth/dist/api/routes/sign-up.mjs:145, 217–264`), `signUpEmail` only rejects public registration when `ctx.options.emailAndPassword?.disableSignUp` is truthy (`L145`). Otherwise, any unauthenticated `POST /api/auth/sign-up/email` with `{ name, email, password }` inserts a new row into `"user"` applying `defaultValue: "staff"` (`lib/auth.ts:45`) and `defaultValue: true` (`lib/auth.ts:51`), creates a `credential` account, issues a live 7-day `session` (`autoSignIn` defaults to `true` at `sign-up.mjs:254`), and returns `Set-Cookie: better-auth.session_token=...`. `requireAdmin()` (`lib/auth-guard.ts:35`) grants full admin access whenever `user.role === "staff"` and `user.isActive !== false`.
- Impact (business terms): Complete unauthenticated administrative takeover in a single HTTP request. Any internet actor can self-register a `staff` admin account and immediately read/export all pilgrim applications, passport details, phone numbers, WhatsApp conversations, wholesale supplier net rates, and quotes, or send live WhatsApp messages, publish to agency social accounts, overwrite Meta WABA credentials (`A02-005`), and upload HTML/SVG payloads to `/uploads/r2-local/` (`A00-003`).
- Root cause: `lib/auth.ts` left Better Auth's public `signUpEmail` endpoint enabled so `createStaffUser` (`app/actions/catalog.ts:876`) and `db/seed.ts:26, 64` could call `auth.api.signUpEmail(...)`, unaware that `toNextJsHandler(auth)` exposes `POST /api/auth/sign-up/email` publicly with default `role = "staff"` and `isActive = true`.
- Recommended fix:
  1. In `lib/auth.ts:37–39`, set `emailAndPassword: { enabled: true, disableSignUp: true }` and remove `signUp` from `lib/auth-client.ts:13`.
  2. Because `disableSignUp: true` also causes `auth.api.signUpEmail(...)` to throw `EMAIL_PASSWORD_SIGN_UP_DISABLED` (`sign-up.mjs:145–149`), refactor `createStaffUser` (`app/actions/catalog.ts:876–883`) and `db/seed.ts` to provision users server-side via `(await auth.$context).password.hash(validated.password)` + `(await auth.$context).internalAdapter.createUser(...)` + `internalAdapter.linkAccount({ accountId: createdUser.id, providerId: "credential", userId: createdUser.id, password: passwordHash })` without minting a session.
- Test to add: Integration test in `tests/integration/auth-signup-blocked.test.ts` sending an unauthenticated `POST /api/auth/sign-up/email` to `auth.handler(req)` asserting HTTP `400` (`EMAIL_PASSWORD_SIGN_UP_DISABLED`) and `0` rows inserted into `"user"`, paired with a test proving `createStaffUser` called by a `super_admin` still creates an active `staff` user who can subsequently sign in.
- Effort: S (<2h)
- Confidence: High
- Needs owner decision: no

### A02-003 — Double Phone-Verification Bypass (`"-------"` and Empty `customerWhatsapp`) & Enumeration Oracle in `lookupApplicationStatus`
- Severity: P0
- Category: security
- Where: `app/actions/applications.ts:51–57, 812–878`; `lib/validations/application.ts:150–156`
- Brief claim contradicted (if any): §6.1 "verified by phone suffix match before returning itinerary"
- Evidence:
  1. `statusLookupSchema` (`lib/validations/application.ts:150–156`) validates `customerPhone: z.string().trim().min(7, "Please enter a valid phone number")` — checking character length only, with **zero digit requirement**.
  2. `lookupApplicationStatus` (`app/actions/applications.ts:824–826`) runs:
     ```ts
     const { referenceNumber, customerPhone } = parseResult.data
     const normalizedInputDigits = cleanPhoneNumber(customerPhone)
     const inputSuffix = normalizedInputDigits.slice(-9) // Last 9 digits match regional phone formats
     ```
     and at `L863–871` verifies:
     ```ts
     const storedPhoneDigits = cleanPhoneNumber(app.customerPhone)
     const storedWhatsappDigits = cleanPhoneNumber(app.customerWhatsapp)

     const matchesPhone =
       storedPhoneDigits.endsWith(inputSuffix) ||
       storedWhatsappDigits.endsWith(inputSuffix) ||
       normalizedInputDigits.endsWith(storedPhoneDigits.slice(-9)) ||
       normalizedInputDigits.endsWith(storedWhatsappDigits.slice(-9))
     ```
  3. **Bypass #1 (100% of applications)**: Passing `customerPhone: "-------"` (7 hyphens) satisfies `.min(7)`. `cleanPhoneNumber("-------")` (`phone.replace(/\D/g, "")` at `L52`) returns `""`, so `inputSuffix` is `""`. In JavaScript, `storedPhoneDigits.endsWith("")` (`L867`) evaluates to **`true` for every string**!
  4. **Bypass #2 (applications with blank `customerWhatsapp`)**: Whenever `app.customerWhatsapp` is `""`, `storedWhatsappDigits.slice(-9)` is `""`, so `normalizedInputDigits.endsWith("")` (`L870`) evaluates to **`true` for any arbitrary phone number** (and if `app.customerWhatsapp` is `null` at runtime, `phone.replace(...)` at `L52` throws an unhandled `TypeError`).
  5. **Enumeration oracle + tiny keyspace**: Missing references (`L855–860`) return `"No application found matching this reference code. Please verify the code."`, whereas phone mismatches (`L872–878`) return `"The phone number provided does not match the contact number registered with this reference code."` across a `32^4 = 1,048,576` `ART-YYYY-XXXX` keyspace (`Math.random()` at `L30`) with **zero rate limiting**. Successful responses (`L953–992`) expose internal UUID `app.id`, `customerFirstName`, `departureCity`, travel dates, passenger breakdown, hotel stays, and quote totals.
- Impact (business terms): Mass unauthenticated disclosure of pilgrim travel schedules, family compositions, hotel stays, quote pricing, and internal application UUIDs across 100% of the customer base without knowing any pilgrim phone number.
- Root cause: `cleanPhoneNumber` strips non-digits *after* Zod's `.min(7)` string length check, leaving empty strings (`""`) unguarded inside `.endsWith(...)` on both `inputSuffix` and `storedWhatsappDigits`, coupled with distinct error messages and a 20-bit reference suffix.
- Recommended fix:
  1. Harden `statusLookupSchema` (`lib/validations/application.ts:155`) to require `cleanPhoneNumber(val).length >= 9` and `<= 15`.
  2. In `app/actions/applications.ts:863–871`, guard against null/empty strings (`storedPhoneDigits.length >= 9` and `storedWhatsappDigits.length >= 9`) and require exact 9-digit suffix equality (`inputSuffix.length === 9 && (storedPhoneDigits.slice(-9) === inputSuffix || (storedWhatsappDigits.length >= 9 && storedWhatsappDigits.slice(-9) === inputSuffix))`), never `.endsWith("")`.
  3. Return an identical generic error message for both missing-reference and phone-mismatch cases, add DB-backed per-IP + per-reference rate limiting (5 attempts / 15 min), and switch reference generation to `crypto.randomInt` with >= 8 chars (`40` bits). Owner decision (§11): confirm whether reference + hardened phone match suffices or if a WhatsApp OTP step should gate quote details.
- Test to add: Unit/integration regression test calling `lookupApplicationStatus({ referenceNumber: "ART-2026-ABCD", customerPhone: "-------" })` and testing an application with `customerWhatsapp: ""` against a wrong phone `"03009999999"`, asserting `success: false` with identical generic error text whether or not `ART-2026-ABCD` exists.
- Effort: S (<2h)
- Confidence: High
- Needs owner decision: yes

### A02-004 — Hardcoded Seed Credentials (`Admin@123456` / `Staff@123456`), Forced Re-Activation on Re-Seed, and No Safe Prod Bootstrap
- Severity: P0

- Where: `db/seed.ts:17–91`

Furthermore, when `db/seed.ts` is re-run on an existing database (`L48–53` and `L86–89`), the `else` branches execute `.update(schema.user).set({ role: "super_admin", isActive: true })` and `.set({ role: "staff", isActive: true })` — forcibly **re-activating** default accounts even if an owner had deactivated them! - Impact (business terms): Running `npm run db:seed` against staging/production (to load catalog hotels/airlines/sectors) plants publicly documented default credentials (`Admin@123456`) with full `super_admin` privileges and revives deactivated seed accounts.

- Test to add: Integration test running seed logic twice after setting `isActive = false` on an existing admin and verifying: (a) production mode rejects missing `BOOTSTRAP_ADMIN_EMAIL`, and (b) re-seeding catalog data never flips `isActive` back to `true`.

### A02-006 — Session Clobbering on `createStaffUser`, Unrevoked Sessions on Deactivation/Role Change, Deactivated Sign-In, and Last-`super_admin` Race
- Severity: P1
- Category: security
- Where: `app/actions/catalog.ts:874–936`; `lib/auth.ts:26–58`; `node_modules/better-auth/dist/integrations/next-js.mjs:72–99`; `app/admin/(dashboard)/layout.tsx:21–25`
- Brief claim contradicted (if any): §6.6 "Immediate staff deactivation and role access control"
- Evidence:
  1. **`createStaffUser` clobbers the calling `super_admin`'s own browser session (`catalog.ts:874–883`)**: Despite the comment `// without passing headers to keep current admin's session intact` (`L874`), `lib/auth.ts:57` enables `nextCookies()`. In `better-auth/dist/integrations/next-js.mjs:72–99`, `nextCookies()` runs an `after` hook on **every** `auth.api.*` call (`matcher: () => true`), calls `await cookies()` from `next/headers`, and executes `cookieHelper.set(key, value.value, ...)` (`L94`) with the newly created staff user's auto-signed-in session cookie — **silently overwriting the `super_admin`'s browser session into the new `staff` user**!
  2. **Sessions never deleted on deactivation or role change**: `toggleUserActive` (`app/actions/catalog.ts:911–914`) and `updateUserRole` (`L929–932`) only `UPDATE "user"` and never execute `DELETE FROM "session" WHERE user_id = $userId`. Although `requireAdmin()` currently re-reads `"user"` from PostgreSQL because `cookieCache` is off, existing 7-day rows in `"session"` remain active: Better Auth's `/api/auth/get-session`, `/api/auth/update-user`, and `/api/auth/change-password` still honor the deactivated user's cookie (`node_modules/better-auth/dist/api/routes/session.mjs:153–215` does not check `user.isActive`), and enabling `cookieCache` later would create a 5-minute revocation bypass.
  3. **Deactivated users can still pass `/api/auth/sign-in/email`**: `lib/auth.ts` defines no `databaseHooks.session.create.before` check on `user.isActive`. A user with `isActive = false` can POST valid credentials to `/api/auth/sign-in/email`, minting fresh rows in `"session"` before `layout.tsx:22–24` redirects `/admin` back to `/admin/login?session_expired=1` (showing a misleading `"Session Expired"` banner instead of `"Account deactivated"`).
  4. **Last-`super_admin` lockout race & stale revalidation**: `toggleUserActive` (`L907`) and `updateUserRole` (`L925`) check only `if (session.user.id === userId)`. Neither checks remaining active `super_admin` count (`WHERE role = 'super_admin' AND is_active = true`), so two `super_admin` users concurrently demoting or deactivating each other leave **zero** active `super_admin` accounts. Also `catalog.ts:901, 916, 934` call `revalidatePath("/admin/users")` (a redirect stub) instead of `revalidatePath("/admin/settings")`.
- Impact (business terms): Creating a staff account immediately logs the Super Admin out into the junior staff account; terminated staff retain live `/api/auth/*` sessions and can repeatedly mint DB sessions; concurrent admin edits can permanently lock the agency out of `super_admin` access.
- Root cause: Calling `auth.api.signUpEmail` under `nextCookies()` inside a Server Action, and adding custom `isActive`/`role` fields without hooking `databaseHooks.session.create.before` or deleting `"session"` rows on state transitions.
- Recommended fix:
  1. Provision staff in `createStaffUser` via `(await auth.$context).internalAdapter.createUser` + `linkAccount` (never `auth.api.signUpEmail`), keeping the calling `super_admin` session untouched.
  2. In `toggleUserActive` (when `!isActive`) and `updateUserRole`, immediately run `await db.delete(schema.session).where(eq(schema.session.userId, userId))` and call `revalidatePath("/admin/settings")`.
  3. Add `databaseHooks: { session: { create: { before: async (session) => { ... } } } }` in `lib/auth.ts` rejecting `user.isActive === false` with `APIError("FORBIDDEN", { message: "Account is deactivated" })`.
  4. Guard `toggleUserActive` and `updateUserRole` with an atomic SQL subquery requiring `(SELECT count(*) FROM "user" WHERE role = 'super_admin' AND is_active = true AND id <> $targetId) >= 1` whenever deactivating or demoting a `super_admin`.
- Test to add: Integration test verifying: (a) `createStaffUser` preserves the caller's `super_admin` cookie, (b) `toggleUserActive(staffId, false)` deletes all `"session"` rows for `staffId`, (c) `POST /api/auth/sign-in/email` for `staffId` fails with `403` and creates `0` session rows, and (d) two `super_admin` accounts cannot leave `0` active `super_admin`s.
- Effort: S (<2h)
- Confidence: High
- Needs owner decision: no

### A02-007 — Production Wildcard Dev-Tunnel `trustedOrigins` CSRF Gap, Conditional `Secure` Cookie Downgrade, and OAuth State/Cookie Leaks

- Test to add: Integration test sending multi-IP `X-Forwarded-For` headers vs platform trusted IP headers to `/api/auth/sign-in/email`, proving User A's `429` after 5 failed attempts does NOT `429` User B from a different client IP, and verifying persistence in the `rate_limit` table.
