### A03-001 — Unescaped Pilgrim & Flyer Inputs in Gotenberg/Chromium HTML Templates Enable Server-Side HTML/JS Injection & Headless Chromium SSRF

- Severity: P0
- Category: security
- Where: `lib/posters/render-quotation-pdf.ts:64–68, 70–137, 185, 333, 388, 518, 552–568` (`sanitizeNoHyphensNoSar`, `buildLuxuryQuotationHtml`, `renderAndUploadLuxuryQuotationPdf`); `lib/posters/render-multi-package-poster.ts:45–81, 232–245`; `lib/posters/render-single-package-poster.ts:50–80, 217–299`; `lib/posters/chromium-cdp.ts:74–90, 175–183, 241–252`; `lib/posters/gotenberg.ts:138–158`; `app/actions/quotes.ts:667, 742`; `../scripts/oracle-gotenberg/docker-compose.yml:8–12, 55–57`
- Brief claim contradicted (if any): `None (gap)`
- Evidence:
  1. None of the four HTML template builders (`render-quotation-pdf.ts`, `render-multi-package-poster.ts`, `render-single-package-poster.ts`, `chromium-cdp.ts`) perform HTML entity escaping (`&`, `<`, `>`, `"`, `'`). In `lib/posters/render-quotation-pdf.ts:64–68`, the sole sanitizer only rewrites `SAR` and word hyphens:
     ```ts
     function sanitizeNoHyphensNoSar(text: string): string {
       return text
         .replace(/\bSAR\b/gi, "PKR")
         .replace(/(\w)-(\w)/g, "$1 $2")
     }
     ```
  2. **Unauthenticated-to-Chromium SSRF data flow (`H13`):**
     - An unauthenticated internet user calls `submitCustomApplication` (`app/actions/applications.ts:80, 186`), where `contact.customerName` is validated only with `z.string().min(3)` (`lib/validations/application.ts:10`) — no `.max()` cap and no character or markup restriction. The server returns the new `referenceNumber` (e.g., `ART-2026-XXXX`) to the caller (`app/actions/applications.ts:353`).
     - When a consultant clicks "Generate Luxury PDF" (`generateApplicationLuxuryPdf` in `app/actions/quotes.ts:667, 742`), `appData.customerName` is passed into `buildLuxuryQuotationHtml` and interpolated directly into `<div class="family-name">${clientName}</div>` (`render-quotation-pdf.ts:333`) and `<div class="total-banner-title">${clientName}</div>` (`L518`), alongside unescaped hotel names, airline names, room summaries, and transport descriptions (`L185, 388–510`).
     - Gotenberg runs with `--chromium-disable-javascript=false` (`../scripts/oracle-gotenberg/docker-compose.yml:9`), zero `--chromium-deny-list` flags (`L8–12`), external bridge egress enabled (`L55–57`), and `waitDelay: "650ms"` (`lib/posters/gotenberg.ts:152`), giving injected HTML/JS elements (`<iframe>`, `<img src>`, `<link>`, `<script>`) 650 ms of active execution inside headless Chromium on the Oracle Cloud VM.
     - If Gotenberg is unset or unreachable, `renderHtmlViaGotenberg` falls back to `renderHtmlViaLocalChromium` (`lib/posters/chromium-cdp.ts:175, 243`), launching local Chrome with `--no-sandbox` (`L175`) and injecting raw HTML into `about:blank` via `Page.setDocumentContent` (`L243`, waited 650 ms at `L252`), where Chromium can also access localhost services and local `file://` paths.
     - `renderAndUploadLuxuryQuotationPdf` (`render-quotation-pdf.ts:566–567`) uploads the rendered PDF to the **public R2 bucket** at deterministic key `quotations/${input.referenceNumber.toLowerCase()}_umrah_quotation.pdf` — turning blind Chromium SSRF into full-read SSRF because the submitter already holds `referenceNumber`.
  3. **Second vector (Studio flyers):** `render-multi-package-poster.ts:232–245`, `render-single-package-poster.ts:217–299`, and `chromium-cdp.ts:74–90` interpolate 100% of AI-extracted supplier flyer strings (`makkahHotelName`, `madinahHotelName`, `daysTitle`, `routePill`, `inclusions`, `airlineName`) and `<img class="airline-img" src="${airlineLogoDataUri}" alt="${airlineName}">` (`chromium-cdp.ts:75`) without HTML/attribute escaping, allowing prompt-injected supplier PDFs/images to trigger Chromium SSRF during poster generation.
- Impact (business terms): An unauthenticated form submitter (or malicious supplier flyer) can read internal cloud metadata (Oracle Cloud IMDS `169.254.169.254`), probe internal Docker/localhost ports, read local host files when the local Chromium fallback triggers, or forge/corrupt official Al Ramlah Travels PDF quotations sent to customers.
- Root cause: Template literals were used to construct full HTML documents for headless Chromium without an HTML-escaping helper, while Gotenberg was configured with JavaScript enabled, no URL deny-list, and deterministic public R2 output paths.
- Recommended fix: Introduce a strict `escapeHtml(value: string)` utility (`&`, `<`, `>`, `"`, `'`) in `lib/posters/escape-html.ts` and wrap every dynamic string and attribute interpolated across `render-quotation-pdf.ts`, `render-multi-package-poster.ts`, `render-single-package-poster.ts`, and `chromium-cdp.ts`; validate image/logo sources in poster templates to accept only `data:image/(png|jpeg|webp);base64,...` or allowlisted `https://` R2 asset origins; harden `../scripts/oracle-gotenberg/docker-compose.yml` by setting `--chromium-disable-javascript=true` and `--chromium-allow-list=^https://fonts\.(googleapis|gstatic)\.com/.*`; and disable `--no-sandbox` local Chrome fallback in `NODE_ENV === "production"`.
- Test to add: Unit test in `tests/posters-xss-ssrf.test.ts` passing `<script>`, `<iframe src="...">`, and `"><img onerror=...>` in `customerName`, `makkahHotel.name`, `airlineLogoDataUri`, and flyer `inclusions`, asserting that `buildLuxuryQuotationHtml`, `buildMultiPackagePosterHtml`, and `buildSinglePackagePosterHtml` emit `&lt;script&gt;` / `&lt;iframe` with zero raw unescaped tags or non-allowlisted URLs.
- Effort: M (<1d)
- Confidence: High
- Needs owner decision: no

### A03-002 — Unrestricted Local Upload Fallback & Inbound WhatsApp Filename Extension Trust Enable Same-Origin Stored XSS

- Severity: P0
- Category: security
- Where: `app/api/uploads/local/route.ts:19–66` (`handleLocalUpload`); `lib/whatsapp/media-mirror.ts:39–48, 178–189` (`resolveExtensionFromMimeType`, `mirrorInboundWhatsAppMedia`); `app/api/uploads/presign/route.ts:6–32, 57–63` (`presignRequestSchema`, `POST`); `lib/storage/r2.ts:197–253, 283–320` (`uploadBufferToR2`, `createPresignedUploadUrl`)
- Brief claim contradicted (if any): §4.1 (`docs/PLATFORM_MASTER_BRIEF.md:552`) "When R2 credentials are unset in local development, uploads fall back transparently"
- Evidence:
  1. **Arbitrary `.html` / `.svg` write to same-origin `public/` via `/api/uploads/local`:**
     - `app/api/uploads/local/route.ts:6–66` is active in **all** environments (including `NODE_ENV=production`), guarded only by `requireAdmin()` (`staff` or `super_admin`).
     - While lines `31–47` check directory containment under `public/uploads/r2-local`, the handler enforces **zero** file extension allowlist, **zero** MIME or magic-byte inspection, and **zero** request size limit (`await req.arrayBuffer()` at `L49`). Note also `L41` (`targetPath !== baseDir`) permits `rawKey="/"` to pass the traversal guard and hit `fs.writeFile(baseDir)` (`EISDIR` 500).
     - Any `staff` account (or `createPresignedUploadUrl` fallback when `filename` ends in `.html` alongside `contentType: "image/png"`, `presign/route.ts:7–20` & `r2.ts:289–299`) can write an `.html` or `.svg` file into `public/uploads/r2-local/`, served directly on the application's primary origin as `text/html` / `image/svg+xml`, executing arbitrary JavaScript with full `super_admin` session cookie scope when visited.
  2. **Unauthenticated WhatsApp attachment filename extension trusted over MIME type (`lib/whatsapp/media-mirror.ts:39–48`):**
     ```ts
     export function resolveExtensionFromMimeType(
       mimeType: string | null | undefined,
       filename?: string | null
     ): string {
       if (filename) {
         const extMatch = filename.trim().match(/\.([a-zA-Z0-9]{2,8})$/)
         if (extMatch?.[1]) {
           return extMatch[1].toLowerCase()
         }
       }
     ```
     An unauthenticated WhatsApp stranger can send a document attachment whose `mediaFilename` ends in `.html`, `.htm`, `.svg`, `.xhtml`, or `.js` (`2–8` alphanumeric chars). `resolveExtensionFromMimeType` returns `html`/`svg` **before** consulting `mimeType` (`L50`), and `mirrorInboundWhatsAppMedia` (`L178–183`) calls `uploadBufferToR2` with `key: .../wamid.html` and `contentType: finalMimeType` (`text/html` or `image/svg+xml`). Crucially, `uploadBufferToR2` (`lib/storage/r2.ts:242–253`) **automatically falls back** to writing `public/uploads/r2-local/${cleanKey}` in production whenever R2 is unconfigured or throws a transient S3/Cloudflare error — executing JavaScript same-origin (or on `r2.alramlahtravels.com`) when staff opens the attachment in `/admin/desk`.
  3. **Presign size & folder bypass:** `app/api/uploads/presign/route.ts:26–31` marks `sizeBytes` as `.optional()`, never forwards `sizeBytes` to `createPresignedUploadUrl` (`L58–62`), and `PutObjectCommand` (`lib/storage/r2.ts:304–308`) omits `ContentLength`, allowing unbounded multi-GB uploads on any presigned URL. `folder` (`presign/route.ts:25`) has no prefix allowlist, allowing a `staff` user to overwrite predictable keys under `quotations/` or `posters/`.
- Impact (business terms): Any unauthenticated WhatsApp sender (when R2 fallback triggers or on custom R2 subdomain) or low-privilege `staff` user can achieve Stored XSS against `super_admin` directors, hijack active admin sessions, exfiltrate the customer/passport database, or exhaust server disk/R2 storage.
- Root cause: `/api/uploads/local` and `uploadBufferToR2` remain enabled in production without extension/magic-byte validation or `Content-Disposition: attachment`, and `resolveExtensionFromMimeType` prioritizes untrusted user filenames over verified magic bytes.
- Recommended fix: Hard-disable `/api/uploads/local` and the `uploadBufferToR2` local-filesystem fallback when `NODE_ENV === "production"` (fail closed if R2 fails rather than writing to `public/`); enforce magic-byte file-signature verification (`image/jpeg`, `image/png`, `image/webp`, `application/pdf`, `audio/ogg`, `video/mp4`) and derive the stored extension **exclusively** from the verified MIME allowlist — never from `filename` (`media-mirror.ts:43`, `presign/route.ts:7`, `uploadRawFlyerFileAction` at `marketing-ops.ts:134`); make `sizeBytes` required in `presignRequestSchema`, cap `/api/uploads/local` body reads at `25 MB` via streaming byte counter, restrict `folder` to `z.enum(["uploads", "flyers", "hotels", "cms"])`, and set `ContentDisposition: "attachment"` on non-image documents uploaded to R2.
- Test to add: Integration tests in `tests/uploads-security.test.ts` verifying: (a) `resolveExtensionFromMimeType("application/pdf", "invoice.html")` returns `"pdf"` (never `"html"` or `"svg"`), (b) `/api/uploads/local` rejects `.html`/`.svg` keys, payloads `> 25 MB`, `key="/"`, and any call when `NODE_ENV=production`, and (c) `/api/uploads/presign` rejects unknown `folder` values and missing `sizeBytes`.
- Effort: M (<1d)
- Confidence: High
- Needs owner decision: no

### A03-003 — Single Public R2 Bucket & Enumerable Keys Expose Pilgrim Passports, WhatsApp Media, Quotation PDFs & Wholesale Flyers, Plus Runtime `~/.wrangler` Token Scraping

- Severity: P0
- Category: security
- Where: `lib/storage/r2.ts:53–82, 187–190, 207–240`; `next.config.ts:37–51`; `lib/posters/render-quotation-pdf.ts:566–568`; `lib/whatsapp/media-mirror.ts:178–189`; `app/actions/applications.ts:38–54`; `app/actions/marketing-ops.ts:134–141`
- Brief claim contradicted (if any): §7.1 (`docs/PLATFORM_MASTER_BRIEF.md:943`) "Official privacy disclosure outlining customer data collection (passports, travel dates)... Cloudflare R2"
- Evidence:
  1. **Single world-readable R2 bucket for both public marketing assets and confidential PII:** `lib/storage/r2.ts:187–190` constructs unconditional public URLs (`${publicBase}/${cleanKey}`) against the public R2 bucket configured in `next.config.ts:38–50` (`pub-7f2c533d31cc45bb9eb2669af5a3b5ef.r2.dev` and `r2.alramlahtravels.com`). Zero presigned `GetObjectCommand` helpers exist anywhere in `lib/storage/r2.ts`.
  2. **Enumerable Quotation PDFs (`1,048,576` total keyspace):** `generateApplicationReference` (`app/actions/applications.ts:38–54`) builds reference codes `ART-${year}-${4 chars}` from a 32-character alphabet (`32^4 = 1,048,576` total combinations per year, using non-cryptographic `Math.random()` at `L44`). `renderAndUploadLuxuryQuotationPdf` (`lib/posters/render-quotation-pdf.ts:566`) uploads every pilgrim's quotation PDF to `quotations/${input.referenceNumber.toLowerCase()}_umrah_quotation.pdf` on the zero-egress public R2 domain — exposing full family names, travel dates, hotels, transport itineraries, and package pricing to unauthenticated enumeration.

  4. **Host developer credential scraping in `r2.ts`:** `resolveWranglerOauthToken()` (`lib/storage/r2.ts:53–82`) reads `~/.wrangler/config/default.toml` and `~/AppData/Roaming/xdg.config/.wrangler/config/default.toml` from disk at runtime (`L207–240`) and uses the developer's personal Cloudflare Wrangler OAuth token for application R2 uploads whenever S3 keys fail or are omitted.
- Impact (business terms): Mass unauthorized disclosure of pilgrim passport/CNIC images, family travel itineraries, payment receipts, and confidential supplier net pricing — creating severe Pakistani data-protection, Saudi Ministry compliance, reputational, and commercial poaching liability.
- Root cause: Public CDN asset delivery (hero banners, social posters) and private document storage (WhatsApp pilgrim media, quotations, raw supplier flyers) share a single public R2 bucket without key unguessability or signed read URLs, paired with a developer convenience fallback that reads `~/.wrangler`.
- Recommended fix: Split storage into two buckets — a public bucket strictly for published marketing posters (`posters/`), hotel/CMS photos (`hotels/`, `cms/`), and public group brochures, and a private bucket (`R2_PRIVATE_BUCKET_NAME`, no public `r2.dev` / custom domain) for `whatsapp-media/`, `quotations/`, and `flyers/raw/`, accessed exclusively via short-lived (`<= 15 min`) presigned `GetObjectCommand` URLs minted behind `requireAdmin()` (or behind a hardened, rate-limited `lookupApplicationStatus` check for the specific pilgrim's quote); switch `generateApplicationReference` (`app/actions/applications.ts:44`) from `Math.random()` to `crypto.randomInt()` and append a 128-bit random capability token to stored quotation filenames; and delete `resolveWranglerOauthToken()` and `uploadViaCloudflareRestApi()` (`lib/storage/r2.ts:53–164, 207–240`). (Owner decision: Provision a second private Cloudflare R2 bucket `al-ramlah-private` vs. disabling public `r2.dev`/custom-domain access on sensitive prefixes via Cloudflare Worker/R2 config.)
- Test to add: Unit tests in `tests/r2-privacy.test.ts` verifying: (a) private object keys (`whatsapp-media/*`, `quotations/*`, `flyers/raw/*`) never return a bare `R2_PUBLIC_URL` and require `createPresignedReadUrl()`, (b) `r2.ts` never accesses `os.homedir()` / `.wrangler`, and (c) quotation keys include a high-entropy random suffix.
- Effort: L (>1d)
- Confidence: High
- Needs owner decision: yes

- Test to add: Unit tests in `tests/safe-media-fetch.test.ts` asserting that `loadMediaBytes` and `resolveImageBuffer` throw on `".env"`, `"/../.env"`, `"file:///etc/passwd"`, `"http://169.254.169.254/latest/meta-data/"`, `"http://127.0.0.1:3000"`, `302` redirects to private IPs, and responses exceeding `maxBytes`.

### A03-007 — Dual Token Vault Cryptographic Defects: Unauthenticated Legacy AES-CBC Oracle, Low-Entropy Key Acceptance, Incompatible Wire Formats & Raw Ciphertext Leak on Decrypt Failure

- Severity: P1
- Category: security
- Where: `lib/whatsapp/encryption.ts:23–50, 64, 97–109`; `lib/social/crypto.ts:10–34, 54`; `lib/env.ts:55–56`; `lib/whatsapp/media-mirror.ts:151–156`; `lib/whatsapp/auto-responder.ts:640–645`; `lib/whatsapp/intake-flow.ts:313–318`

- Evidence:
  1. **Unauthenticated legacy AES-256-CBC decryption path (`lib/whatsapp/encryption.ts:97–109`):** When `trimmed.split(":")` has 2 segments (`ivHex:encryptedHex`), `decrypt()` silently switches to `crypto.createDecipheriv("aes-256-cbc", key, iv)` with **zero HMAC/MAC authentication**.   2. **Silent SHA-256 hashing of weak keys in production & secret reuse in non-prod:** `ENCRYPTION_KEY` is `.optional()` in `lib/env.ts:56`.   3. **Two incompatible AES-256-GCM wire formats in the same app:** `lib/whatsapp/encryption.ts:64` serializes `ivHex:encryptedHex:authTagHex` (`iv:ct:tag`, hex), whereas `lib/social/crypto.ts:54` serializes `ivB64:tagB64:ciphertextB64` (`iv:tag:ct`, base64) — guaranteeing cross-module decryption bugs and key-rotation hazards.
  4. **Ciphertext / unencrypted-token leak to external API on `decrypt()` error (`lib/whatsapp/media-mirror.ts:151–156`, repeated in `auto-responder.ts:640–645` and `intake-flow.ts:313–318`):**

     ```ts
     try {
       accessToken = decrypt(account.encryptedAccessToken)
     } catch {
       accessToken = account.encryptedAccessToken
     }
     ```
     When decryption fails (e.g., rotated `ENCRYPTION_KEY`), the server transmits the raw database `encryptedAccessToken` vault string over HTTPS in `Authorization: Bearer ...` headers to Meta's servers instead of failing closed.
- Impact (business terms): Compromises the confidentiality and integrity of Meta WhatsApp System User tokens, Baileys Signal private keys, and Core 5 Social OAuth access/refresh tokens; risks leaking vault ciphertexts to third-party logs during key rotation or misconfiguration.

- Test to add: Unit tests in `tests/vault-crypto.test.ts` verifying: (a) 2-part CBC strings are rejected, (b) `NODE_ENV="production"` throws at startup if `ENCRYPTION_KEY` is missing or not 64 hex chars, (c) tampered auth tags or IV lengths (`!== 12` bytes) throw, and (d) `mirrorInboundWhatsAppMedia` aborts without calling `fetch` when `decrypt()` fails.

- Severity: P2
- Category: security
- Where: `lib/whatsapp/auto-responder.ts:447, 460, 493–503` (`matchKeywordAutoReplyRule`); `lib/validations/whatsapp-crm.ts:116–128` (`whatsappAutoReplyRuleSchema`)
- Brief claim contradicted (if any): `None (gap)` — contradicts `lib/whatsapp/auto-responder.ts:447` inline JSDoc claim ("safety against invalid/ReDoS patterns")
- Evidence:
  In `lib/whatsapp/auto-responder.ts:460, 493–503`:
  ```ts
  const safeRegexInput = normalizedText.slice(0, 1000)
  // ...
  } else if (rule.matchType === "REGEX") {
    // Safety guard: reject overly long patterns (> 120 chars) and wrap compilation in try/catch
    if (kw.length > 120) continue
    try {

    }
  ```

  Capping pattern length at `120` characters and wrapping `new RegExp(kw, "i")` in `try/catch` **only catches syntax errors, not Regular Expression Denial of Service (`ReDoS`)**. V8's `RegExp` engine uses backtracking NFA evaluation: a short pattern (`< 15` chars) containing nested quantifiers (configured accidentally or maliciously by any `staff` user via `upsertWhatsappAutoReplyRuleAction`) evaluated against a `1,000`-character non-matching inbound WhatsApp text triggers exponential $O(2^n)$ backtracking on the main thread, blocking the Node.js or Trigger.dev worker event loop.
- Impact (business terms): A single malformed `REGEX` auto-reply rule combined with a normal-length inbound WhatsApp message can freeze the `process-inbound-whatsapp` worker (or Next.js inline webhook fallback), stalling all customer auto-replies, package PDF dispatches, and inbox updates.
- Root cause: Relied on string-length heuristics (`<= 120` chars on pattern, `<= 1000` chars on input) instead of a linear-time `O(n)` regex engine (`re2`) or static nested-quantifier AST validation (`safe-regex2`) at rule creation time.
- Recommended fix: Validate `REGEX` keywords inside `whatsappAutoReplyRuleSchema` (`lib/validations/whatsapp-crm.ts:121`) and `matchKeywordAutoReplyRule` using `re2` (linear-time Google RE2 engine) or reject patterns containing nested quantifiers / backreferences via `safe-regex2` before saving to `whatsapp_auto_reply_rules`.
- Test to add: Unit test in `tests/auto-responder-redos.test.ts` verifying that `whatsappAutoReplyRuleSchema` rejects nested-quantifier `REGEX` patterns (e.g., `(a+)+$`) with a validation error while allowing safe alternation/word-boundary patterns (`\b(makkah|madinah)\s+hotel\b`) in `< 5 ms` on a 1,000-character input.
