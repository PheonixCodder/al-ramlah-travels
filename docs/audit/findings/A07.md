## P0 Findings — Stop-Ship

### A07-001 — Two-stage seat overselling: public `submitGroupBookingApplication` never holds seats, and concurrent admin approvals overwrite `bookedSeats` (Lost Update)

- Severity: P0
- Category: data-integrity
- Where: `app/actions/applications.ts:408–429, 471–559`; `components/public/group-booking-modal.tsx:219–223, 566–568`; `app/actions/quotes.ts:122–200, 386–463`; `db/schema/packages.ts:99–138`
- Brief claim contradicted (if any): §9.2.1 (`docs/PLATFORM_MASTER_BRIEF.md:1220`) "Reserves seats on seasonal group departure batches."
- Evidence:
  1. **Stage 1 (Public Submission)**: `submitGroupBookingApplication` (`app/actions/applications.ts:408–429`) reads `availableSeats = departure.totalSeats - departure.bookedSeats`, inserts `applications` (`L471`) and `applicationQuotes` (`L511`), **never updates `group_departures.booked_seats`**, omits `revalidatePath("/")` (`L538–541`), and returns unchanged `remainingSeats: availableSeats` (`L557`). Meanwhile, `GroupBookingModal` (`components/public/group-booking-modal.tsx:219–222, 567`) tells the pilgrim: *"Group Booking Reserved! Your group seats ... have been provisionally held."*
  2. **Stage 2 (Admin Approval Lost Update & Non-Transactional Drift)**: In both `saveApplicationQuote` (`app/actions/quotes.ts:149–180`) and `updateApplicationStatus` (`app/actions/quotes.ts:405–428`), `newBookedSeats` is computed in JavaScript from a stale `SELECT` (`Math.min(totalSeats, departure.bookedSeats + requestedSeats)`) and written as a literal value (`SET booked_seats = ${newBookedSeats}`) instead of an atomic SQL expression (`booked_seats + ${requestedSeats}`). When two admins concurrently approve `2` seats each on a `4`-seat batch (`booked_seats = 0`), both read `0`, both compute `newBookedSeats = 2`, and the second `UPDATE ... WHERE total_seats - booked_seats >= 2` still evaluates `4 - 2 >= 2` (`TRUE`), overwriting `booked_seats = 2` instead of `4`! The exact same stale JS lost-update race affects seat release (`Math.max(0, departure.bookedSeats - requestedSeats)` at `quotes.ts:182–200, 443–460`), and because `db/index.ts` uses `neon-http` with zero transaction around `group_departures` + `applications` updates, any failure on `applications` permanently desynchronizes `booked_seats`.
  3. **Live Disposable PostgreSQL Proof (`alramlah-audit-pg` on `127.0.0.1:54329`, cleaned up to `0|0|0`)**:
     ```text
     === A07 H23 Seat Oversell & Schema Constraint Proof (alramlah-audit-pg) ===
     Created temp package=0d6940c8-0580-4562-bb44-5cddab2f5c46, temp batch=868bafb4-1fc6-4655-bad8-670bacc86d5c (total_seats=4, booked_seats=0)

     [PROOF 1 - Public Submission Oversubscription]
     Submissions accepted: 5/5 families of 4 seats each (all reportedRemainingSeats: 4)
     DB state (total_seats|booked_seats|status|app_count|sum_bed_and_seat_count): 4|0|open|5|20

     [PROOF 2 - Concurrent Admin Approval Lost-Update Oversell (quotes.ts:405-428)]
     Admin A: {"adminLabel":"AdminA_App1_2seats","success":true,"readBooked":0,"wroteBooked":2,"updated":"2|open\nUPDATE 1"}
     Admin B: {"adminLabel":"AdminB_App2_2seats","success":true,"readBooked":0,"wroteBooked":2,"updated":"2|open\nUPDATE 1"}
     Admin C: {"adminLabel":"AdminC_App3_2seats","success":true,"readBooked":2,"wroteBooked":4,"updated":"4|sold_out\nUPDATE 1"}
     DB state (total_seats|booked_seats|status|approved_apps|actual_approved_seats): 4|4|sold_out|3|6

     [CLEANUP VERIFICATION] (leftover_apps|leftover_pkgs|leftover_deps): 0|0|0
     ```
- Impact (business terms): Unlimited families receive confirmation screens claiming their seats are `"Reserved / Provisionally Held"` on the last remaining flight block, and two consultants approving bookings in `/admin/desk` physically oversell fixed airline PNR allotments (`6` approved seats on a `4`-seat flight block = **150% physical oversell**), exposing Al Ramlah Travels to emergency spot-ticket buyouts in PKR or stranded pilgrims.
- Root cause: Public submission performs a pure unguarded read with zero seat hold, while admin approval/release computes `newBookedSeats` and `newBatchStatus` in JavaScript from a non-locked `SELECT` rather than an atomic SQL `SET booked_seats = booked_seats + $n` inside a real database transaction.
- Recommended fix:
  1. Replace JavaScript read-modify-write in `quotes.ts` (`L149–200, L405–461`) with a single atomic SQL `UPDATE group_departures SET booked_seats = booked_seats + ${requestedSeats}, status = CASE WHEN status = 'closed' THEN 'closed'::departure_status WHEN booked_seats + ${requestedSeats} >= total_seats THEN 'sold_out'::departure_status WHEN (booked_seats + ${requestedSeats})::numeric / NULLIF(total_seats, 0) >= 0.8 THEN 'filling_fast'::departure_status ELSE 'open'::departure_status END WHERE id = ${depId} AND status NOT IN ('closed', 'sold_out') AND booked_seats + ${requestedSeats} <= total_seats RETURNING *` (and symmetric atomic decrement `GREATEST(0, booked_seats - ${requestedSeats})` on release), executed inside a WebSocket Pool (`Pool` from `@neondatabase/serverless`) transaction alongside the `applications` status update.
  2. Add PostgreSQL `CHECK (booked_seats >= 0 AND booked_seats <= total_seats)` on `group_departures`.
  3. (Owner decision: Should public `submitGroupBookingApplication` place a time-boxed provisional seat hold — e.g., `held_seats` + `seat_hold_expires_at` 24h TTL before auto-expiry — or deduct seats strictly when staff mark the booking `approved` after deposit, updating public modal copy from `"Group Booking Reserved / Provisionally Held"` to `"Booking Request Submitted — Seats confirmed upon deposit verification"`?)
- Test to add: Real-Postgres integration test firing `Promise.all` with 5 concurrent `2`-seat approvals against a `4`-seat `group_departures` row and asserting exactly `2` succeed (`booked_seats = 4, status = 'sold_out'`) and `3` fail cleanly with `0` oversold seats.

### A07-002 — Cross-package `groupPackageId` / `groupDepartureId` mismatch lets callers book a 5-Star VIP flight batch at Economy rates

- Severity: P0
- Category: security
- Where: `app/actions/applications.ts:408–459, 478–482`; `lib/validations/application.ts:135–141`
- Brief claim contradicted (if any): §6.1 (`docs/PLATFORM_MASTER_BRIEF.md:788`) "Fixed-Departure Group Packages Grid & instant online seat booking modal."
- Evidence:
  - `submitGroupBookingApplication` (`app/actions/applications.ts:408–437`) fetches `departure` by `data.groupDepartureId` (`L408–410`) and `pkg` by `data.groupPackageId` (`L431–433`) **without checking `departure.packageId === pkg.id`**.
  - Rate calculation (`L440–455`) falls back to `pkg.*PricePkr` whenever `departure.*PriceOverridePkr` is `null`:
    ```ts
    // app/actions/applications.ts:452-455
    } else if (data.selectedRoomType === "quad") {
      ratePerPersonPkr = departure.quadPriceOverridePkr ?? pkg.quadPricePkr
    }
    ```
  - In `db/seed.ts:2092–2106`, Royal VIP batch `ART-RAM-ISB-01` (`quadPricePkr = 485,000` on its parent VIP package) has `quadPriceOverridePkr: null, triplePriceOverridePkr: null, doublePriceOverridePkr: null`. Calling `submitGroupBooking` with Economy Bronze `groupPackageId` (`quadPricePkr = 262,099`) and Royal VIP `groupDepartureId` (`ART-RAM-ISB-01`) creates an application + `application_quotes` row on the VIP flight batch at **PKR 262,099/pax** instead of **PKR 485,000/pax** — a **PKR 222,901 per-pilgrim underquote** (`PKR 891,604` loss on a 4-adult quad booking).
- Impact (business terms): Any unauthenticated caller crafting a POST payload to `submitGroupBooking` can pair a low-tier Economy package ID with a high-tier Ramadan/5-Star departure batch that lacks per-batch price overrides, generating an official `ART-...` booking dossier and WhatsApp confirmation message misquoted hundreds of thousands of PKR below net cost.
- Root cause: Missing relational integrity check (`departure.packageId !== pkg.id`) between the two independently queried UUIDs in `submitGroupBookingApplication`.
- Recommended fix: Query `departure` joined with its parent `groupPackages` row via `departure.packageId` (or enforce `if (departure.packageId !== pkg.id) return { success: false, error: "Selected departure batch does not belong to the chosen package." }`) before computing prices or inserting `applications`.
- Test to add: Integration test passing `groupPackageId = pkgBronze.id` and `groupDepartureId = vipBatch.id` to `submitGroupBookingApplication` and asserting `{ success: false }` with zero rows inserted.

      .update(schema.applications)

When an admin deletes a supplier flyer in Studio that was previously published as a public Group Package (`publishedGroupPackageId`), `deleteSupplierFlyerAction` forcibly wipes `groupPackageId = null` and `groupDepartureId = null` across **all** `applications` (including `approved` and `quoted` paying families) to bypass PostgreSQL's `23503` FK constraint, and then hard-deletes the `group_packages` row and cascade-deletes all its `group_departures` batches.
