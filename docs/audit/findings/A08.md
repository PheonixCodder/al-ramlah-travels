## Detailed Findings (§3.3 Format)

### A08-001 — Unauthenticated Status Tracker Empty-Suffix Auth Bypass, 20-Bit Predictable Reference Keyspace, Enumeration Oracle & Full Itinerary/PDF Leak
- Severity: P0
- Category: security
- Where: `web/app/actions/applications.ts:25-49, 812-989`, `web/lib/validations/application.ts:150-156`, `web/app/actions/quotes.ts:665-733, 789-798`
- Brief claim contradicted (if any): §6.1 "enter their reference number (`ART-YYYY-XXXX`) and phone number to inspect real-time quotation status"
- Evidence: Building on `A02-003` and `A03-011` with an exact field-level audit of `lookupApplicationStatus`: (1) `statusLookupSchema` (`lib/validations/application.ts:155`) validates `customerPhone: z.string().trim().min(7, "Enter matching phone number")` without requiring digits. Passing `customerPhone: "-------"` (7 hyphens) passes Zod; `cleanPhoneNumber("-------")` (`applications.ts:51-57`) returns `""`, `inputSuffix = "".slice(-9)` (`L826`) is `""`, and `storedPhoneDigits.endsWith("")` (`L867`) evaluates to `true` in JavaScript for every string—bypassing phone verification for 100% of applications. Conversely, if `app.customerWhatsapp` is `""` (e.g., fallback `waPhone || ""` in `lib/whatsapp/intake-flow.ts:753`), `storedWhatsappDigits.slice(-9)` is `""` and `normalizedInputDigits.endsWith("")` (`L870`) also returns `true` for any phone input. (2) `generateApplicationReference()` (`applications.ts:25-49`) uses non-cryptographic `Math.random()` over a 32-char alphabet (`32^4 = 1,048,576` total 4-char codes per year) and is unnecessarily `export`ed from a `"use server"` file (`L35`), creating a public callable Server Action that executes up to 5 DB `SELECT`s per call. (3) `lookupApplicationStatus` (`L855-860` vs `L872-878`) returns distinct error strings for unknown reference vs phone mismatch (an enumeration oracle), uses case-insensitive pattern operator `ilike(schema.applications.referenceNumber, cleanRef)` (`L832`) instead of exact indexed equality `eq()`, and has zero rate limiting. (4) Upon bypass, lines `891-988` return internal UUID `app.id`, `customerName`, `customerCity`, travel dates, passenger counts, full `hotelStays`, `transportSegments`, `groupBookingDetails` (flight numbers, airline, batch code), itemized PKR quote totals, `amountPaidPkr`, `quoteNotesCustomer`, and **`quotationPdfUrl`** (`L983` — publicly accessible R2 PDF URL rendered via `quotes.ts:665-733` that additionally embeds wholesale `supplierName` at `L729`). Note: `customerEmail`, `customerPhone`, and `specialRequests` are not directly serialized in the JSON object (`L894-968`).
- Impact (business terms): Any unauthenticated third party or competitor can enumerate Al Ramlah Travels' active booking pipeline (`ART-2026-XXXX`), bypass phone verification on every valid code using `"-------"`, harvest VIP pilgrim names, cities, travel dates, family composition, hotel rooms, flight numbers, wholesale supplier names (via the exposed `quotationPdfUrl` PDF), and exact PKR pricing/discounts—constituting a severe pilgrim PII and commercial intelligence breach.
- Root cause: `statusLookupSchema` allows digit-free strings; `endsWith` suffix matching is evaluated without guarding `inputSuffix.length >= 9` and `storedPhoneDigits.length >= 9`; reference codes rely on 20 bits of `Math.random()` entropy with distinct error messages and zero rate limiting; `generateApplicationReference` is exported from a `"use server"` module.
- Recommended fix: Remove `export` from `generateApplicationReference` (move to `lib/domain/reference.ts` using `crypto.randomInt` with >=8-char suffix or opaque lookup token). In `statusLookupSchema`, require >=9 digits after stripping non-digits (`z.string().max(32)`). In `lookupApplicationStatus`, enforce `normalizedInputDigits.length >= 9` and guard `storedPhoneDigits.length >= 9` / `storedWhatsappDigits.length >= 9` before constant-time comparison, unify not-found and mismatch responses into a single generic error, replace `ilike` with `eq`, strip `app.id` and wholesale `supplierName` from public artifacts, sign `quotationPdfUrl` with short-lived presigned R2 URLs, and enforce IP + reference rate limiting.
- Test to add: Unit and integration test `tests/actions/lookup-application-status.test.ts` asserting `customerPhone: "-------"`, `"       "`, `"++++++++"`, wrong phone on blank-WhatsApp rows, and mismatched phones all return the identical generic failure with `application: undefined` and `quote: undefined`.
- Effort: M (<1d)
- Confidence: High
- Needs owner decision: no

Connect directly with our concierge team:"* + *"Accept & Proceed via WhatsApp"* and renders **zero link or download button for a booking voucher**. (3) The only voucher route in the codebase is `/admin/applications/[id]/voucher` (`app/admin/(dashboard)/applications/[id]/voucher/page.tsx:25-28`), which is blocked from public pilgrims twice: `proxy.ts:32-38, 45` redirects every unauthenticated `/admin/:path*` request without a `better-auth.session_token` cookie to `/admin/login`, and `PrintBookingVoucherPage` (`voucher/page.tsx:28`) calls `await requireAdmin()`. Add a signed public voucher route or Gotenberg R2 voucher PDF exposed in `StatusTracker` **only** when `app.status === "approved"`, and guard `voucher/page.tsx` so non-approved applications show a clear draft watermark or block issuance.

- Confidence: High

### A08-003 — Broken Leading-Zero `wa.me/03...` Deep Links Across Public Contact Card, Status Tracker Accept CTA & Admin Web Messages Desk

- Evidence: `DEFAULT_COMPANY_INFO.primaryWhatsapp` (`lib/company-info.ts:28`) and the fallback in `lookupApplicationStatus` (`app/actions/applications.ts:883`) store the agency WhatsApp number in local Pakistani leading-zero format `"03274029701"` (`0327 4029701` in `DEFAULT_COMPANY_INFO`). Three separate UI surfaces in A08 strip non-digits without converting leading `03` to `923` (`H28`): (1) `ContactSection` (`components/public/contact-section.tsx:137`): `href={\`https://wa.me/${info.primaryWhatsapp.replace(/[^0-9]/g, "")}\`}` produces `https://wa.me/03274029701`. (2) `StatusTracker` (`components/public/status-tracker.tsx:686`): `href={\`https://wa.me/${agencyWhatsapp.replace(/\D/g, "")}?text=...\`} ` produces `https://wa.me/03274029701?text=...` on the primary `"Accept & Proceed via WhatsApp"` button. (3) Admin `MessagesClient` (`components/admin/catalog/messages-client.tsx:306` in `/admin/desk?tab=web_messages`): `href={\`https://wa.me/${selectedMessage.whatsapp.replace(/[^0-9]/g, "")}\`}` produces `https://wa.me/03...` whenever a pilgrim enters a domestic number matching the form placeholder `placeholder="0327 4029701"` (`contact-section.tsx:278, 290`).
- Impact (business terms): Clicking `"Primary WhatsApp Desk"` in the Contact section, clicking `"Accept & Proceed via WhatsApp"` on a live quotation in the Status Tracker, or clicking `"WhatsApp Pilgrim"` inside the Admin Web Messages inbox fails with WhatsApp's invalid phone number error—dropping high-intent pilgrims at the exact moment of quote acceptance and breaking staff outbound follow-up.
- Root cause: Ad-hoc inline `.replace(/[^0-9]/g, "")` / `.replace(/\D/g, "")` calls instead of a shared E.164 WhatsApp URL helper (`lib/phone.ts` only handles PK numbers and is not used by any of these three components; see `A05-011`).
- Recommended fix: Create a single shared `buildWhatsAppUrl(rawPhone: string, text?: string)` utility in `lib/phone.ts` that normalizes `+...`, `00...` (strip leading `00`), and domestic PK `03XXXXXXXXX` (`-> 923XXXXXXXXX`), and replace all inline `wa.me` string interpolations in `contact-section.tsx:137`, `status-tracker.tsx:686`, `messages-client.tsx:306`, `hajj-inquiry-section.tsx:1013`, and `applications.ts:51-62`.
- Test to add: Unit test `tests/lib/whatsapp-url.test.ts` verifying `buildWhatsAppUrl` produces `https://wa.me/923274029701` for `"0327 4029701"`, `"+92 327 4029701"`, and `"00923274029701"`, while preserving international numbers like `"+44 7911 123456"` (`https://wa.me/447911123456`).

- Confidence: High
- Needs owner decision: no

### A08-006 — Public Contact Form Action Uses Uncaught `.parse()` & Unbounded Strings Causing Unhandled Server Exceptions & PostgreSQL `VARCHAR(32)` Crashes
