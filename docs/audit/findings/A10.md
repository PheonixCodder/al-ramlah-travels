### A10-001 — Unescaped pilgrim input in Gotenberg HTML enables JS execution and cloud SSRF (`H13`)
- Severity: P0
- Category: security
- Where: `lib/posters/render-quotation-pdf.ts:64–68, 132–137, 328–334, 387–390, 414–475`, `scripts/oracle-gotenberg/docker-compose.yml:8–11, 54–57`, `app/actions/quotes.ts:665–733`
- Brief claim contradicted (if any): §7.2 "renders luxury branded multi-page PDF quotations via Oracle Gotenberg Chromium"
- Evidence: `buildLuxuryQuotationHtml` in `lib/posters/render-quotation-pdf.ts` interpolates unauthenticated applicant strings (`input.customerName`, `input.referenceNumber`, hotel names, flight routes) directly into raw HTML without escaping `<`, `>`, `&`, `"`, or `'`. Its only helper, `sanitizeNoHyphensNoSar` (`L64–68`), strips `\bSAR\b` and word-internal hyphens (which also corrupts `"Al-Ramlah"` into `"Al Ramlah"` and ISO dates `"2026-11-14"` into `"2026 11 14"`):
  ```ts
  function sanitizeNoHyphensNoSar(text: string): string {
    return text
      .replace(/\bSAR\b/gi, "PKR")
      .replace(/(\w)-(\w)/g, "$1 $2")
  }
  ```
  At `L330` and `L388`, `const clientName = sanitizeNoHyphensNoSar(input.customerName)` is injected directly into `<title>`, `<div class="cover-client-name">${clientName}</div>`, `<div class="info-card-value">${clientName}</div>`, and `<div class="total-banner-title">`. Simultaneously, `scripts/oracle-gotenberg/docker-compose.yml:8–11, 54–57` launches Gotenberg Chromium with JavaScript explicitly enabled (`--chromium-disable-javascript=false`), zero `--chromium-deny-list`, and an external-egress Docker bridge network (`gotenberg_internal`). Submitting `<script>fetch('http://169.254.169.254/opc/v1/instance/').then(r=>r.text()).then(t=>document.body.innerText=t)</script>` as `customerName` (up to 120 chars via `customApplicationSchema`, or `<iframe src="http://169.254.169.254/opc/v1/instance/metadata" width="800" height="800">`) executes inside headless Chromium when staff clicks `"3-Page Luxury PDF"` and writes the exfiltrated response to the public R2 PDF URL.
- Impact (business terms): Any anonymous internet visitor submitting a lead form can trigger Server-Side Request Forgery (SSRF) against Oracle Cloud IMDS (`169.254.169.254`), internal container endpoints (`http://localhost:3000`), or local container files (`file:///etc/passwd`) inside the Gotenberg VM and read the output from the public quotation PDF, or deface official agency quotations.
- Root cause: `buildLuxuryQuotationHtml` constructs HTML via string templates with zero `escapeHtml()` encoding, while the Gotenberg container leaves Chromium JS enabled and omits URL deny-lists.
- Recommended fix: (1) Add a strict `escapeHtml(value: string)` utility encoding `&`, `<`, `>`, `"`, and `'` and wrap every dynamic interpolation in `lib/posters/render-quotation-pdf.ts` (and fix `sanitizeNoHyphensNoSar` so ISO dates and `"Al-Ramlah"` are not mangled). (2) Harden `scripts/oracle-gotenberg/docker-compose.yml` with `--chromium-disable-javascript=true` (none of the PDF/poster templates require runtime JS) and `--chromium-deny-list=^file://.*,^http://169\.254\..*,^http://127\..*,^http://localhost.*,^http://10\..*,^http://172\.(1[6-9]|2[0-9]|3[0-1])\..*,^http://192\.168\..*`.
- Test to add: Unit test calling `buildLuxuryQuotationHtml` with `customerName: '<img src=x onerror=alert(1)><iframe src="http://169.254.169.254"></iframe>'` asserting zero raw `<img` or `<iframe` tags appear in the rendered HTML output.
- Effort: S (<2h)
- Confidence: High
- Needs owner decision: no

### A10-002 — Opening or saving Quote Worksheet on `group_booking` zeroes `grandTotalPkr`
- Severity: P0
- Category: data-integrity
- Where: `components/admin/applications/quote-worksheet-form.tsx:104–127, 315–323, 1196, 1214`, `app/actions/applications.ts:511–526`, `app/actions/quotes.ts:68–75, 206–238`, `app/admin/(dashboard)/applications/[id]/page.tsx:110–150`
- Brief claim contradicted (if any): §7.2 "Group bookings display fixed package tier pricing ... itemized quote worksheet"
- Evidence: When a pilgrim books a fixed group package, `submitGroupBookingApplication` (`app/actions/applications.ts:511–526`) inserts an `application_quotes` row with `grandTotalPkr: packageTotalPkr` (e.g., `1,100,000`) while setting all 6 itemized pillar columns (`visaTotalPkr`, `flightsTotalPkr`, `makkahHotelTotalPkr`, `madinahHotelTotalPkr`, `transportTotalPkr`, `ziyaratTotalPkr`) to `0`. When staff opens `/admin/applications/[id]`:
  1. `calculateApplicationRateHints` (`app/admin/(dashboard)/applications/[id]/page.tsx:110–150`) has no `group_booking` branch (`hotelStays` and `transportSegments` are empty), so it computes only a standalone ~PKR 35,250 visa hint instead of the group room-tier rate.
  2. `QuoteWorksheetForm` (`quote-worksheet-form.tsx:104–127, 315–323`) initializes its 6 number inputs from the `0` pillar fields and computes `subtotalPkr = 0` and `grandTotalPkr = 0`, immediately displaying `Grand Total: PKR 0` on screen while disabling `"Save & Mark Quoted"` (`L1196`) and `"Approve Booking"` (`L1214`) because `grandTotalPkr <= 0`.
  3. Clicking `"Save Draft Quote"` (for example, to record an advance `amountPaidPkr` or internal consultant note) invokes `saveApplicationQuote` (`app/actions/quotes.ts:68–75, 208–238`), which recomputes `grandTotalPkr = 0` from the 6 zeroed pillars and overwrites `applicationQuotes.grandTotalPkr` in Postgres from `1,100,000` to `0`.
- Impact (business terms): Every group package booking opened in the Quote Desk appears as `PKR 0` in the worksheet, blocks 1-click booking approval until staff manually invents fake pillar splits to match the group total, and wipes out the stored package revenue (`PKR 0`) if staff saves a draft note or deposit.
- Root cause: `submitGroupBookingApplication` stores the lump-sum group tier total only in `grandTotalPkr` (leaving all 6 pillar columns at `0`), whereas both `QuoteWorksheetForm` and `saveApplicationQuote` assume `grandTotalPkr` is strictly the sum of the 6 custom-builder pillars minus `discountPkr`.
- Recommended fix: Either (a) add a `groupPackageTotalPkr` column (or populate itemized pillars on `submitGroupBookingApplication` / `QuoteWorksheetForm` when `source === "group_booking"` using `selectedRoomType * chargeablePax + infantVisaTicketPkr`), or (b) detect `source === "group_booking"` when all 6 pillars are `0` and `initialQuote.grandTotalPkr > 0` so the worksheet preserves/displays the group package base line item and includes it in `saveApplicationQuote`'s server-side sum.
- Test to add: Integration test creating a `group_booking` application with `grandTotalPkr = 620000`, saving an internal note + `amountPaidPkr = 200000` via `saveApplicationQuote`, and asserting `grandTotalPkr` remains `620000` with `paymentStatus = "partially_paid"`.
- Effort: M (<1d)
- Confidence: High
- Needs owner decision: yes

### A10-004 — Unrestricted status state machine, non-transactional seat drift, and zero `audit_logs` (`H25`)
- Severity: P0
- Category: data-integrity
- Where: `app/actions/quotes.ts:122–201, 368–507`, `db/index.ts:1–20`, `db/schema/applications.ts:42–48, 139–227`
- Brief claim contradicted (if any): §7.2 "Atomic Seat Inventory Management: Approving a group booking atomically increments bookedSeats"
- Evidence: Four compounding state-machine and concurrency defects exist in `app/actions/quotes.ts`:
  1. **Zero transition matrix (`L99–115, 368–383`)**: Any `staff` user can execute arbitrary jumps: `rejected -> approved`, `cancelled -> approved`, `pending_quote -> approved` (skipping `quoted` and with `paymentStatus = "unpaid"` / `amountPaidPkr = 0`, requiring only `latestGrandTotal > 0` at `L374`), or `approved -> pending_quote`.
  2. **Silent seat loss when re-quoting an approved booking (`L138, 436`)**: Both `saveApplicationQuote` (`L138`) and `updateApplicationStatus` (`L436`) release group departure seats whenever `previousStatus === "approved" && targetStatus !== "approved"`. If a consultant edits an approved group booking and clicks `"Save & Mark Quoted"` (`targetStatus = "quoted"`), the customer's confirmed seats are silently released back to public inventory and can be bought by another party!
  3. **Non-transactional seat updates + non-atomic seat release (`L159–171, 192–199, 415–425, 453–461`)**: `db/index.ts` uses `drizzle-orm/neon-http`, which does not wrap `groupDepartures` updates and `applications` updates in a SQL transaction. If `db.update(applications)` (`L296` or `L485`) fails after `db.update(groupDepartures)` (`L160` or `L415`) succeeds, `bookedSeats` permanently drifts from actual `approved` applications. Moreover, while seat deduction uses an atomic SQL `WHERE totalSeats - bookedSeats >= requestedSeats` (`L162`), seat release (`L192, 453`) performs an unsafe JS read-modify-write (`const newBookedSeats = Math.max(0, departure.bookedSeats - requestedSeats)`), losing seat releases when two cancellations race. (Note: moving `rejected`/`cancelled -> approved` *does* hit `L387` to re-reserve seats, subject to the same non-transactional drift.)
  4. **Zero audit trail**: Across all 43 database tables in `db/schema/*`, there is no `audit_logs` table and no `updatedByUserId` / `approvedByUserId` column on `applications`; `decisionAt` and `quoteSentAt` (`L475–483`) are overwritten in place without recording which staff member changed prices, approved an unpaid booking, or cancelled seats.
- Impact (business terms): Confirmed pilgrims can lose their departure seats during a routine quote amendment; `bookedSeats` can drift out of sync on transient network errors or concurrent cancellations (overselling or stranding seats); and agency owners have zero forensic record of who approved bookings, overrode prices, or marked cash received.
- Root cause: Status updates accept any target enum value without an allowed-transition graph, `neon-http` lacks multi-statement transactions (`Pool` / `neon-serverless` WebSocket driver is needed for `db.transaction()`), seat release uses JS arithmetic instead of SQL `GREATEST(0, booked_seats - N)`, and no audit-logging table was modeled.
- Recommended fix: (1) Enforce an explicit transition map in `lib/domain/application-state-machine.ts` (blocking `pending_quote -> approved` without `quoted` + required payment, blocking `rejected`/`cancelled -> approved` without explicit reopen to `pending_quote`/`quoted`, and requiring confirmation before moving `approved` to a non-approved state that releases seats). (2) Execute seat mutations + status updates + an `application_audit_logs` insert (`actorUserId`, `fromStatus`, `toStatus`, `beforeJson`, `afterJson`, `createdAt`) inside a real Postgres transaction via `@neondatabase/serverless` `Pool` (`drizzle-orm/neon-serverless`), using atomic SQL `GREATEST(0, ${groupDepartures.bookedSeats} - ${requestedSeats})` on release.
- Test to add: Concurrency & state-machine integration test against local Postgres proving illegal transitions (`rejected -> approved`, `pending_quote -> approved` unpaid) throw, two parallel cancellations decrement `bookedSeats` by `2 * requestedSeats`, and every status/price mutation writes an `application_audit_logs` row with `actorUserId`.
- Effort: L (>1d)
- Confidence: High
- Needs owner decision: yes

### A10-005 — Predictable public R2 quotation PDF keys leak client PII and serve stale prices after quote edits (`H14`)
- Severity: P1
- Category: security
- Where: `lib/posters/render-quotation-pdf.ts:565–568`, `app/actions/quotes.ts:206–238, 665–735`, `app/actions/whatsapp-crm.ts:890–899`, `app/actions/applications.ts:983`, `components/admin/applications/quote-dispatch-bar.tsx:60–85`
- Brief claim contradicted (if any): §7.2 "Pilgrims view real-time status, itemized PKR quotes, and PDF downloads"
- Evidence: `renderAndUploadLuxuryQuotationPdf` (`lib/posters/render-quotation-pdf.ts:566`) uploads every quotation to a fixed, unversioned, publicly readable R2 key:
  ```ts
  const key = `quotations/${input.referenceNumber.toLowerCase()}_umrah_quotation.pdf`
  const uploaded = await uploadBufferToR2(pdfBuffer, key, "application/pdf")
  ```
  1. **PII enumeration (`H14`)**: `referenceNumber` uses a 4-character alphabet suffix (`ART-YYYYMM-XXXX`, `32^4` = 1,048,576 combinations per month). Anyone scraping `https://<R2_PUBLIC_URL>/quotations/art-202611-xxxx_umrah_quotation.pdf` (no phone verification required, bypassing `lookupApplicationStatus`) can harvest full pilgrim names, cities, travel dates, hotel stays, and PKR package quotes.
  2. **Stale PDF served after price edits**: When staff edits pillar prices in `saveApplicationQuote` (`app/actions/quotes.ts:208–238`), `quotationPdfUrl` is **not** cleared or invalidated. Consequently, `lookupApplicationStatus` (`app/actions/applications.ts:983`) and `sendApplicationLuxuryPdfViaWhatsappAction` (`app/actions/whatsapp-crm.ts:890` — `let pdfUrl = app.quotes?.[0]?.quotationPdfUrl; if (!pdfUrl) { ... }`) continue serving and WhatsApp-sending the **old PDF containing superseded prices**! Even when regenerated, reusing the exact same R2 key causes Cloudflare/browser caches to serve stale bytes.
  3. **Unsaved form race (`PKR 0` PDF)**: Clicking `"3-Page Luxury PDF"` in `QuoteDispatchBar` (`quote-dispatch-bar.tsx:68`) or `"Generate 3-Page Luxury PDF"` in `QuoteWorksheetForm` (`quote-worksheet-form.tsx:260`) before clicking `"Save"` reads DB state (`PKR 0` on fresh custom leads) instead of current form inputs; and in cloud Trigger mode (`quote-worksheet-form.tsx:577–584`), `QuoteDispatchBar`'s `useState(activeQuote?.quotationPdfUrl)` (`L60`) never syncs when props refresh.
- Impact (business terms): Competitors or scrapers can enumerate client itineraries and pricing from public R2 without phone verification, while pilgrims receive outdated PDFs showing old (potentially lower) PKR totals after a consultant updates flight or hotel rates.
- Root cause: Quotation PDFs use a static `referenceNumber`-based key on the public marketing R2 prefix, `saveApplicationQuote` leaves `quotationPdfUrl` intact when prices mutate, and PDF generation does not auto-save dirty worksheet state.
- Recommended fix: (1) Store quotation PDFs under a private prefix or non-guessable versioned key (`quotations/${app.id}/v${quote.version}-${crypto.randomUUID()}.pdf`) served via short-lived presigned URLs after phone+ref or admin auth verification. (2) Clear `quotationPdfUrl = null` inside `saveApplicationQuote` whenever any price, stay, or note changes. (3) Auto-save dirty worksheet state (or disable `"Generate PDF"` while form is dirty) and sync `QuoteDispatchBar` state with `activeQuote?.quotationPdfUrl`.
- Test to add: Integration test verifying that updating `flightsTotalPkr` via `saveApplicationQuote` resets `quotationPdfUrl` to `null` and that regenerating a PDF produces a distinct versioned key rather than overwriting the prior URL.

### A10-006 — Quote revision history overwritten in-place at `version = 1` with zero optimistic locking (`H24`)
- Severity: P1
- Category: data-integrity
- Where: `app/actions/quotes.ts:203–270`, `db/schema/applications.ts:282–331`, `lib/validations/quote.ts:10–35`
- Brief claim contradicted (if any): §8.3 "version: Quote revision counter"
- Evidence: Although `application_quotes` defines `version: integer("version").default(1).notNull()` (`db/schema/applications.ts:289`) and every query sorts by `orderBy: [desc(applicationQuotes.version)]`, `saveApplicationQuote` (`app/actions/quotes.ts:203–270`) never increments `version` or inserts a new revision row when a quote already exists:
  ```ts
  const existingQuote = app.quotes[0]
  if (existingQuote) {
    await db
      .update(applicationQuotes)
      .set({ ... }) // overwrites version 1 in-place!
      .where(eq(applicationQuotes.id, existingQuote.id))
  } else {
    await db.insert(applicationQuotes).values({ ..., version: 1, ... })
  }
  ```
  Because `submitCustomApplication`, `submitGroupBookingApplication`, and `submitHajjInquiryApplication` all pre-create a `version: 1` row at submission time, `existingQuote` is always truthy for web leads — `version` stays `1` forever and prior quotes are permanently overwritten. Conversely, on `ART-WA-*` WhatsApp intake leads (which start with zero quote rows), `db/schema/applications.ts:327–330` lacks a `UNIQUE(application_id, version)` index and has no `isLatest` boolean, so two concurrent first-saves insert duplicate `version = 1` rows with non-deterministic `desc(version)` ordering. Finally, neither `quoteUpdateSchema` (`lib/validations/quote.ts`) nor `saveApplicationQuote` accepts `expectedUpdatedAt` / `expectedVersion`, so two staff members with the same dossier open overwrite each other's prices, notes, and `paymentStatus` via silent last-write-wins.
- Impact (business terms): When a pilgrim disputes a price change ("Yesterday your PDF said PKR 410,000, today it says PKR 465,000"), management has zero historical record of previous quote versions, and two consultants working the Desk Inbox + Pipeline simultaneously can silently overwrite each other's quotes.
- Root cause: `saveApplicationQuote` mutates `app.quotes[0]` in place instead of appending `version: existingQuote.version + 1` (or archiving revisions on `"Save & Mark Quoted"`), lacks a unique `(application_id, version)` constraint, and omits optimistic concurrency checks.
- Recommended fix: (1) Add `UNIQUE(application_id, version)` on `application_quotes` and pass `expectedUpdatedAt` (or `baseQuoteId` + `baseVersion`) in `quoteUpdateSchema`, returning a `CONFLICT` error if another staff member saved in the interim. (2) Increment `version` by inserting a new immutable `application_quotes` row whenever a sent quote (`status === "quoted"` or `"approved"`, or on `"Save & Mark Quoted"`) is revised, exposing a read-only revision history dropdown on `/admin/applications/[id]`.
- Test to add: Integration test simulating two concurrent `saveApplicationQuote` calls from stale `expectedUpdatedAt` snapshots asserting the second call fails with a concurrency conflict instead of clobbering the first save, plus asserting re-quoting increments `version` from `1` to `2`.
- Effort: M (<1d)
- Confidence: High
- Needs owner decision: no
