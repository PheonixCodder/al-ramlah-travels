### A14-001 — Inbound Webhook Violates <150ms Target and Permanently Drops Media/Bot Pipeline on Dispatch Failure (H30)
- Severity: P0
- Category: reliability
- Where: `web/app/api/webhooks/whatsapp/route.ts:184-806`, `web/trigger/dispatch.ts:183-264`, `web/trigger/dispatch.ts:608-642`, `web/trigger/process-inbound-whatsapp.task.ts:62-335`, `web/trigger/mirror-whatsapp-media.task.ts:31-48`, `web/trigger/mirror-whatsapp-media.task.ts:76`
- Brief claim contradicted (if any): `AGENTS.md` ("asynchronous decoupled Meta webhook task `process-inbound-whatsapp.task.ts` with <150ms HTTP response") and Brief §6.5 ("Inbound pilgrim media mirroring to Cloudflare R2").
- Evidence: Before returning `Response.json({ status: "ok" })` at `route.ts:806`, `POST /api/webhooks/whatsapp` executes nested `for` loops (`entry` -> `changes` -> `smb_message_echoes` / `statuses` / `messages`) performing 6–10 sequential `neon-http` SQL queries plus a Trigger `idempotencyKeys.create` network call (`dispatch.ts:617`) per item. Worse, `dispatchInboundWhatsAppProcessing` delegates to `triggerByIdBackgroundOrInline` (`dispatch.ts:183-264`): (1) when `TRIGGER_SECRET_KEY` starts with `tr_dev_` without an attached worker, `dispatch.ts:196` blocks inside the HTTP webhook for `2,200ms` per message (`setTimeout(..., 2200)`) and then runs `runProcessInboundWhatsappInline` (R2 media upload + 3.5s OpenRouter LLM call + Meta Graph sends) synchronously; (2) when Trigger Cloud throws or inline execution fails, `whatsappMessages` has already been committed at `route.ts:750`, `dispatch.ts:252-263` and `route.ts:795-800` catch and swallow all errors while returning HTTP `200`, and `route.ts:503-510` (`if (existingMsg) continue`) permanently skips any subsequent retry. Additionally, `runMirrorWhatsappMediaTask` (`mirror-whatsapp-media.task.ts:33-47`) returns `{ success: false }` instead of throwing (defeating `maxAttempts: 3`), and `dispatchMirrorWhatsAppMedia` (`L76`) reuses static `idempotencyKey: wa-media-mirror-${messageId}` so clicking "Mirror to R2" in Desk returns the stale failed run without re-executing.
- Impact (business terms): During any Trigger.dev outage, transient Neon/R2 blip, or dev-key misconfiguration, Meta webhooks either time out (triggering retry storms across multi-message batches) or silently return `200 OK` while permanently dropping passport/payment receipt media archival (Meta's temporary media URL expires in 5 minutes), AI intent classification, blue-tick read receipts, and pilgrim auto-replies.
- Root cause: Synchronous per-item DB persistence is coupled to non-transactional background dispatch that swallows errors after writing the deduplication key (`wamid`), combined with inline fallback logic designed for interactive UI actions rather than strict `<150ms` webhook ingestion.
- Recommended fix: Persist raw verified webhook payloads into an `inbound_webhook_events` outbox table in a single query and return `200 OK` immediately (<50ms), or add a `processing_status` (`pending` | `completed` | `failed`) column on `whatsapp_messages` so failed dispatches are retried by a cron sweeper instead of skipped by `if (existingMsg) continue`. Remove inline fallback from the webhook path, throw on `!result.success` inside `runMirrorWhatsappMediaTask`, and append a retry nonce or TTL to manual `mirrorInboundWhatsAppMediaAction` idempotency keys.
- Test to add: Integration test in `web/tests/whatsapp-webhook-h30-reliability.test.ts` simulating `tasks.trigger` rejection after `POST /api/webhooks/whatsapp`: assert either HTTP `500` (so Meta retries and re-triggers unassigned work) or outbox recovery without losing media mirroring and auto-reply execution; assert manual media re-mirroring executes a fresh attempt after an initial failure.
- Effort: M (<1d)
- Confidence: High
- Needs owner decision: no

### A14-002 — Non-Atomic Webhook `wamid` & Conversation Upserts Cause `23505` Crashes and Lost Unread Counts Under Retry Storms
- Severity: P1
- Category: data-integrity
- Where: `web/app/api/webhooks/whatsapp/route.ts:309-366`, `web/app/api/webhooks/whatsapp/route.ts:503-510`, `web/app/api/webhooks/whatsapp/route.ts:628-773`, `web/db/schema/whatsapp-crm.ts:214-219`, `web/db/schema/whatsapp-crm.ts:266`
- Brief claim contradicted (if any): Brief §6.5 / Audit scope claim of `wamid` idempotency under Meta retry storms.
- Evidence: Both `smb_message_echoes` (`route.ts:309-365`) and inbound `messages` (`route.ts:503-510`, `L750-773`) perform a non-atomic check-then-act `SELECT id FROM whatsapp_messages WHERE wamid = $1` followed ~250 lines later by `db.insert(whatsappMessages).values(...)` with no `.onConflictDoNothing()`. Likewise, first-time conversations (`route.ts:628-696`) check `SELECT ... FROM whatsapp_conversations` then run `db.insert(whatsappConversations)` against unique index `idx_wa_conv_acc_phone (account_id, contact_phone)` with no `onConflictDoUpdate`. Existing conversations (`L662-674`) update `unreadCount: conversation.unreadCount + 1` using a stale JS integer rather than `sql\`${whatsappConversations.unreadCount} + 1\``.
- Impact (business terms): When Meta retries a slow webhook or a pilgrim sends two photos simultaneously as their first contact, concurrent requests race past the `SELECT` and crash with unhandled PostgreSQL `23505` unique-constraint errors (`500 Internal Server Error`). Worse, in multi-message batches, messages processed earlier in the loop increment `unreadCount` before a later message throws `500`, inflating unread badges on every Meta retry while concurrent messages overwrite each other's `unreadCount + 1`.
- Root cause: Reliance on application-level `SELECT`-before-`INSERT` and read-modify-write counters over stateless `neon-http` queries without PostgreSQL `ON CONFLICT` clauses.
- Recommended fix: Upsert `whatsapp_conversations` atomically via `.onConflictDoUpdate({ target: [whatsappConversations.accountId, whatsappConversations.contactPhone], set: { unreadCount: sql\`${whatsappConversations.unreadCount} + 1\`, ... } })` and insert `whatsapp_messages` with `.onConflictDoNothing({ target: whatsappMessages.wamid }).returning({ id: whatsappMessages.id })`, skipping downstream dispatch and counter increments when `.returning()` yields 0 rows.
- Test to add: Concurrency test firing `Promise.all([POST(req), POST(req)])` with identical `wamid` and simultaneous new-contact payloads against `alramlah_audit` Postgres; assert zero `500` responses, exactly 1 conversation row, 1 message row, and `unread_count === 1`.
- Effort: S (<2h)
- Confidence: High
- Needs owner decision: no

### A14-003 — Out-of-Order Status Webhooks Regress Message Ticks and Drop Early Receipts Arriving Before Outbound DB Insert
- Severity: P1
- Category: data-integrity
- Where: `web/app/api/webhooks/whatsapp/route.ts:372-493`, `web/app/actions/whatsapp-crm.ts:749-851`, `web/lib/whatsapp/auto-responder.ts:786-884`, `web/trigger/send-whatsapp-broadcast.task.ts:389-424`
- Brief claim contradicted (if any): Brief §6.5 ("Broadcast Delivery Funnel" and live delivery/read status tracking).
- Evidence: (1) At `route.ts:386-402`, status webhooks execute `db.update(whatsappMessages).set({ status: st.status }).where(eq(whatsappMessages.wamid, wamid))` with **zero state-progression check**. Although `whatsappBroadcastRecipients` (`L427-433`) guards against `read` -> `delivered`/`sent` regression, `whatsappMessages` does not: if Meta delivers `"delivered"` or `"read"` before `"sent"` (routine on Cloud API), the late `"sent"` webhook downgrades the chat bubble back from blue double-ticks to single grey tick. (2) Every outbound send path (`whatsapp-crm.ts:750-845`, `auto-responder.ts:787-829`, `send-whatsapp-broadcast.task.ts:389-413`) awaits `POST graph.facebook.com/.../messages` first and writes `wamid` to PostgreSQL **after** the HTTP response returns. When Meta's webhook (`sent`/`delivered`/`failed`) arrives during that RTT gap before the DB `INSERT`/`UPDATE` commits, `WHERE wamid = ...` matches `0` rows and returns `200 OK`, permanently losing the delivery/failure status and `whatsappBroadcasts.deliveredCount` / `failedCount` increments.
- Impact (business terms): Staff see blue read-ticks revert to single grey ticks in the Live Desk Inbox, and broadcast campaign funnels under-report `Delivered`, `Read`, and `Failed` counts whenever Meta pushes fast webhook receipts.
- Root cause: Missing monotonic rank comparison (`pending < sent < delivered < read`) on `whatsapp_messages` updates, and no unmatched-status buffer/retry for `wamid`s still in flight from `graph.facebook.com`.
- Recommended fix: Enforce monotonic status ordering in SQL (`WHERE status NOT IN ('read')` when setting `'delivered'`, and `WHERE status NOT IN ('delivered', 'read')` when setting `'sent'`), and persist unmatched `statuses` into a short-lived `whatsapp_pending_status_receipts (wamid, status, error_message, created_at)` table reconciled on outbound `wamid` insert (or schedule a 5-second delayed re-apply when `rowCount === 0`).
- Test to add: Unit/DB test applying status webhooks in reverse order (`read` -> `delivered` -> `sent`) and asserting `whatsapp_messages.status` stays `"read"`, plus simulating a `delivered` receipt arriving 50ms before outbound `wamid` persistence and verifying reconciliation updates both `whatsapp_messages` and `whatsappBroadcasts.deliveredCount`.
- Effort: M (<1d)
- Confidence: High
- Needs owner decision: no

### A14-004 — Predictable Hardcoded `GET` Webhook Verify Tokens and Default-Account Fallback on Unknown `phone_number_id`
- Severity: P1
- Category: security
- Where: `web/app/api/webhooks/whatsapp/route.ts:53-65`, `web/app/api/webhooks/whatsapp/route.ts:284-291`, `web/lib/whatsapp/linked-device.ts:224`, `web/app/actions/whatsapp-crm.ts:2756`, `web/components/admin/hubs/connections-settings-client.tsx:1060`, `web/lib/validations/whatsapp-crm.ts:22`
- Brief claim contradicted (if any): `AGENTS.md` / Brief §6.5 WABA multi-account isolation and secure webhook verification.
- Evidence: While `POST` signature verification (`lib/whatsapp/webhook-signature.ts:47-52`) properly fails closed (`401`) when `META_APP_SECRET` is unset (`verifyMetaWebhookSignature('{}', sig, '') === false`), `GET /api/webhooks/whatsapp` (`route.ts:53-65`) accepts `hub.verify_token` matching **any** active row in `whatsapp_accounts`. Multiple code paths seed static, publicly guessable tokens into active rows: `linked-device.ts:224` inserts `webhookVerifyToken: "linked_device_default_token"`, `completeEmbeddedSignupCoexistenceAction` (`whatsapp-crm.ts:2756`) hardcodes `"art_wa_token_verified"`, `connections-settings-client.tsx:1060` falls back to `"art_wa_token_default"`, and `upsertWhatsappAccountSchema` (`validations/whatsapp-crm.ts:22`) uses non-cryptographic `Math.random()`. Furthermore, on `POST` (`route.ts:284-291`), if `change.value.metadata.phone_number_id` matches no configured account, the webhook falls back to `eq(whatsappAccounts.isDefault, true)` instead of ignoring the event.
- Impact (business terms): Any attacker who knows the codebase defaults can pass Meta's `GET` callback verification challenge against the endpoint, and if a second test/sandbox or partner WABA number is attached to the same Meta App (valid `META_APP_SECRET` HMAC), its inbound messages and status receipts are silently merged into Al Ramlah's primary customer inbox and trigger auto-replies from the primary agency line.
- Root cause: Static fallback verify tokens written during Linked Device and Coexistence onboarding, `Math.random()` token generation, and a permissive `isDefault` account fallback in `route.ts:284-291`.
- Recommended fix: Generate verify tokens exclusively via `crypto.randomBytes(24).toString("hex")` on the server, exclude `LINKED_DEVICE` shadow accounts from Meta Cloud `GET` challenge matching, reject hardcoded default strings, and drop (`continue` + `console.warn`) webhook `changes` whose `metadata.phone_number_id` does not match an active `whatsapp_accounts.phone_number_id`.
- Test to add: Route handler test asserting `GET /api/webhooks/whatsapp?hub.mode=subscribe&hub.verify_token=linked_device_default_token` returns `403`, and `POST` with valid HMAC but unknown `phone_number_id` inserts 0 rows into the default account.
- Effort: S (<2h)
- Confidence: High
- Needs owner decision: no

### A14-005 — Catastrophic Backtracking ReDoS in `REGEX` Keyword Auto-Reply Rules & Cross-Account Rule Leakage (H19)
- Severity: P0
- Category: security
- Where: `web/lib/whatsapp/auto-responder.ts:460`, `web/lib/whatsapp/auto-responder.ts:492-503`, `web/lib/whatsapp/auto-responder.ts:955-959`, `web/lib/validations/whatsapp-crm.ts:577-579`, `web/components/admin/desk/whatsapp-auto-reply-studio.tsx:573`
- Brief claim contradicted (if any): `AGENTS.md` ("Custom Keyword Auto-Reply Rules Engine `matchKeywordAutoReplyRule` with `CONTAINS`/`EXACT`/`STARTS_WITH`/`REGEX`").
- Evidence: `upsertWhatsappAutoReplyRuleSchema` (`validations/whatsapp-crm.ts:578`) accepts any non-empty string (`z.string().trim().min(1)`) for `REGEX` keywords without syntax checking, length caps, or `safe-regex`/RE2 linear-time validation. At runtime, `matchKeywordAutoReplyRule` (`auto-responder.ts:460, 494-499`) slices inbound stranger messages to `1,000` chars (`normalizedText.slice(0, 1000)`) and executes `new RegExp(kw, "i").test(safeRegexInput)` synchronously on the V8 event loop. Empirically verified via `tsx`: a 9-character rule `^(a+)+$` took `108.98ms` on 21 `'a'`s + `'b'` and hung V8 for `>30,000ms` at just 28 `'a'`s + `'b'` (`2^N` blowup; 50–1,000 `'a'`s freezes the worker for days). Additionally, `runWhatsappAutoResponder` (`auto-responder.ts:955-959`) queries `whatsappAutoReplyRules` with `where(eq(whatsappAutoReplyRules.isActive, true))` **missing `eq(whatsappAutoReplyRules.accountId, input.accountId)`**, leaking rules across separate WABA lines.
- Impact (business terms): An accidental nested quantifier entered by staff (e.g., `^(umrah\s*)+$` or `(.*a){10}`) allows a single 40-character WhatsApp message from any stranger on the internet to lock up the Trigger.dev worker or Next.js serverless CPU until hard timeout, halting all inbound WhatsApp processing; meanwhile, rules configured for a Dedicated Agent line fire on the Founder Coexistence line.
- Root cause: Unvalidated user-supplied patterns passed directly to backtracking `new RegExp()` on 1,000-character untrusted inputs, plus missing `accountId` predicate in `runWhatsappAutoResponder`.
- Recommended fix: Validate `REGEX` rules on save with `re2` (linear-time `O(n)` engine) or reject nested quantifiers/backreferences via AST check (`safe-regex2`) + `<=120` char Zod max, execute regex matching via `re2`, and add `and(eq(whatsappAutoReplyRules.isActive, true), eq(whatsappAutoReplyRules.accountId, input.accountId))` at `auto-responder.ts:958`.
- Test to add: Unit test in `web/tests/whatsapp-redos-and-account-isolation.test.ts` asserting `upsertWhatsappAutoReplyRuleSchema` rejects `^(a+)+$` and `(a|aa)+$`, matching a 1,000-char payload completes in `<10ms`, and Account A's active rules never fire on Account B's inbound message.
- Effort: S (<2h)
- Confidence: High
- Needs owner decision: no
