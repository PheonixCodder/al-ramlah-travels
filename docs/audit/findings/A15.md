The Baileys Linked-Device WhatsApp Engine (`lib/whatsapp/linked-device.ts`) cannot function in the target production architecture (**Vercel Serverless + Trigger.dev Cloud + Neon HTTP PostgreSQL**):

1. **Multi-Process & Serverless Split-Brain (`A15-001`, `H4`)**: Active Baileys Noise/WebSocket connections live exclusively in process-local `globalThis.__baileysLinkedDeviceSockets` (`socketMap`). On Vercel, sockets freeze/terminate as soon as `startLinkedDeviceConnectionAction` returns (`linked-device.ts:567`), often before the blind `1,200ms` `setTimeout` (`L532`) even requests an 8-digit pairing code. On Trigger.dev Cloud, `send-whatsapp-group-campaign` runs in a separate worker container where `socketMap` is always empty, failing **100% of automated group/status dispatches**. Conversely, spinning up a second Baileys socket from PostgreSQL credentials in Trigger.dev immediately triggers WhatsApp stream conflict `440` (`DisconnectReason.connectionReplaced`). Even on a single-container VPS, missing `515` (`restartRequired`) reconnect (`A15-002`) and zero boot-time socket rehydration leave `whatsapp_linked_device_sessions.status = "connected"` stale in PostgreSQL while `socketMap` is empty—falsely displaying `"Live Socket Active"` across Settings, Campaigns, and Desk.
2. **Database & Signal State Corruption (`A15-003`, `A15-004`, `A15-005`, `H18`)**: `whatsapp_linked_device_sessions` is completely missing from `web/drizzle/` migrations (`W0-002`); `syncRealWhatsappGroups` crashes with PostgreSQL `42P10` against partial unique indexes (`A15-003`); `purgeFakeMarketingChannelsAction` wipes all Core 5 Instagram/Facebook/TikTok/YouTube/GMB rows (`A15-004`); and `initPostgresBaileysAuthState` re-serializes, AES-256-GCM encrypts, and overwrites the entire monolithic Signal key ring (`pre-key`, `session`, `sender-key`, `lid-mapping`, `tctoken`) over `neon-http` on every event without row locking or error propagation—risking `Bad MAC` ratchet corruption and silent fresh-identity wipes (`A15-005`).
3. **Protocol, JID & ToS Defects (`A15-007`–`A15-011`, `H28`)**: Pakistani `03xx` numbers are formatted into invalid `03xx@s.whatsapp.net` JIDs (`A15-007`); Baileys v7 RC `@lid` (Linked ID) messages are 100% dropped (`A15-008`); WhatsApp Status broadcasts omit `statusJidList` and therefore transmit to `0` recipients (`A15-009`); inbound linked-device messages drop all media (`mediaUrl: null`) and bypass Trigger/auto-replies/opt-out (`A15-010`); and unthrottled custom `1s` delays + identical media re-uploads expose founder SIMs (`+92 321...`) to permanent Meta WhatsApp bans (`A15-011`).

### A15-001 — Broken multi-process & serverless Baileys socket topology (`H4`)
- Severity: P0
- Category: infra
- Where: `web/lib/whatsapp/linked-device.ts:35-38, 172-180, 532-549, 567, 832-855`, `web/app/actions/whatsapp-linked-device.ts:238-254, 406-459`, `web/trigger/send-whatsapp-group-campaign.task.ts:154-160, 280-293`
- Brief claim contradicted (if any): `PLATFORM_MASTER_BRIEF.md` §6.4 (`L827-848`) & `AGENTS.md` claim Trigger.dev Cloud durable background tasks execute automated Safe WhatsApp Group & Status campaigns using linked companion sessions.
- Evidence: `socketMap` is stored on `globalThis.__baileysLinkedDeviceSockets` (`linked-device.ts:35-38`). In `app/actions/whatsapp-linked-device.ts:420-425`, when `process.env.TRIGGER_SECRET_KEY` is configured, `dispatchAutomatedWhatsappGroupsCampaignAction` triggers `send-whatsapp-group-campaign` on Trigger.dev Cloud (`send-whatsapp-group-campaign.task.ts:280`). Inside Trigger.dev's isolated container, `socketMap` is empty, so `sendLinkedDeviceMessage` (`linked-device.ts:851-854`) throws `"Linked device [...] is not currently connected"` for every target channel; `L221` catches the error without rethrowing, logging `"failed"` rows in `daily_post_distributions` and returning `{ success: false }`. Conversely, when `TRIGGER_SECRET_KEY` is absent (`whatsapp-linked-device.ts:441`), `void runSendWhatsappGroupCampaignInline(payload)` runs detached without `after()`, which Vercel terminates when the HTTP response closes; similarly `initBaileysSocket` returns at `L567` before QR scan or the `setTimeout(..., 1200)` pairing-code request (`L532`). Finally, `getLinkedDeviceStatus` (`linked-device.ts:178`) evaluates `isConnected: isMemoryActive || session?.status === "connected"`, reporting dead post-restart DB rows as live active sockets across Settings, Campaigns (`campaigns-hub-client.tsx:3476`), and Desk (`desk-hub-client.tsx:606-609`).
- Impact (business terms): 100% of automated WhatsApp Group and Status campaigns fail in production on Vercel + Trigger.dev Cloud, QR/pairing setup hangs intermittently on serverless functions, and staff see deceptive green `"Live Socket Active"` indicators in Admin Settings and Desk even when zero sockets are running—causing outside-24h pilgrim replies (`app/actions/whatsapp-crm.ts:686,703-739`) to fail instead of prompting for a Meta-approved template.
- Root cause: Stateful, single-owner WhatsApp Web Noise/WebSocket connections (`makeWASocket`) were placed inside stateless Next.js Server Actions while background campaign loops were dispatched to remote Trigger.dev containers with no RPC bridge or outbox consumer, and status queries conflated stale PostgreSQL `status = "connected"` metadata with actual live socket liveness.
- Recommended fix: Select one architecture from §11.1 above: either **(Option A)** sunset Baileys automation in favor of Meta Cloud API + the 100% ban-safe Manual Assisted WA Group/Status Queue, or **(Option C / B)** isolate Baileys into a single persistent Node sidecar (e.g., on the existing Oracle Cloud Always Free VM behind Caddy HMAC RPC, or a 1-replica worker consuming a `whatsapp_linked_outbox` table) with a 30-second `last_heartbeat_at` lease so UI `isConnected` is true only when `now() - last_heartbeat_at < 60s`.
- Test to add: Integration topology test mocking separate Web and Worker module contexts to verify campaign dispatch routes via outbox/RPC (or assisted queue under Option A) and that `getLinkedDeviceStatus` returns `isConnected: false` when heartbeat lease is expired despite `status === "connected"`.
- Effort: L (>1d)
- Confidence: High
- Needs owner decision: yes

### A15-002 — Missing `515` (`restartRequired`) reconnect & premature `sock.user.id` check break pairing and drop live sessions
- Severity: P1
- Category: reliability
- Where: `web/lib/whatsapp/linked-device.ts:53-67, 310-406, 531-549, 841-851`, `web/app/actions/whatsapp-crm.ts:686, 703-705`
- Brief claim contradicted (if any): `PLATFORM_MASTER_BRIEF.md` §6.4 claims 1-click QR scan and 8-digit phone-number pairing seamlessly establish persistent companion sessions.
- Evidence: In `@whiskeysockets/baileys@7.0.0-rc14` (`node_modules/@whiskeysockets/baileys/lib/Socket/socket.js:728-743, 791-796`), immediately after a phone scans a QR code or enters an 8-digit pairing code (`pair-success`), WhatsApp closes the Noise stream with `DisconnectReason.restartRequired` (`515`) so the client opens a fresh authenticated socket. However, `linked-device.ts:368-405` handles only `DisconnectReason.loggedOut` (`401`) and treats **every other close code** (including `515 restartRequired`, `408 timedOut`, `428 connectionClosed`, `503 unavailableService`) identically: `socketMap.delete(sessionKey)` (`L372`) + DB `status: "disconnected", lastError: "Stream Errored (restart-required)"` (`L392-399`) with zero auto-reconnect! Second, during 8-digit code pairing, `sock.requestPairingCode()` (`socket.js:601-606`) assigns `authState.creds.me = { id: "923...@s.whatsapp.net", name: "~" }` **before** the user types the code on their phone (`creds.registered === false`). Because `isLinkedDeviceConnected` (`linked-device.ts:53-57`), `isAnyLinkedDeviceConnected` (`L62-67`), and `sendLinkedDeviceMessage` (`L841-851`) check only `Boolean(sock.user?.id)` without checking `sock.authState.creds.registered === true` and active `connection === "open"` state, an unpaired socket waiting for code input registers as `"connected"` and hijacks expired-24h Cloud API Desk replies (`whatsapp-crm.ts:686,703-705`).
- Impact (business terms): Staff scanning a QR code or entering an 8-digit pairing code see the session immediately drop to `"Disconnected — Stream Errored"` and must manually click reconnect; transient Wi-Fi/WhatsApp server blips permanently kill the companion connection until manual intervention; and initiating a pairing code request briefly breaks Desk 24-hour Meta template enforcement.
- Root cause: The `connection.update` close handler omitted Baileys' mandatory `DisconnectReason.restartRequired` (`515`) + exponential-backoff reconnect state machine, and connection-readiness predicates checked `sock.user?.id` (`creds.me`) instead of tracking `connection === "open"` and `sock.authState.creds.registered`.
- Recommended fix: If Baileys is retained (§11.1 Option B/C), track an explicit `connectionStateMap` (`"connecting" | "open" | "closed"`) requiring `connectionState === "open" && Boolean(sock.authState?.creds?.registered)` in `isLinkedDeviceConnected`, and automatically re-invoke `initBaileysSocket` with bounded exponential backoff + jitter on close codes other than `DisconnectReason.loggedOut` (`401`) and `DisconnectReason.connectionReplaced` (`440`—which should surface a clear duplicate-worker alert).
- Test to add: Unit test simulating Baileys `connection.update` events (`pair-success` -> `close` with `statusCode: 515` -> automatic re-init -> `open`), plus asserting `isLinkedDeviceConnected` returns `false` when `sock.user.id` is set via `requestPairingCode` while `creds.registered === false`.
- Effort: M (<1d)
- Confidence: High
- Needs owner decision: no

### A15-003 — Missing `whatsapp_linked_device_sessions` migration (`W0-002`) & `42P10` unique-index mismatch breaking `syncRealWhatsappGroups`

- Recommended fix: Generate and commit a clean forward Drizzle migration creating `whatsapp_linked_device_status` and `whatsapp_linked_device_sessions` (if Option B/C is chosen) and normalizing `idx_channel_external_id` on `marketing_channels (external_group_id_or_handle)` (remembering PostgreSQL standard `UNIQUE` indexes already allow multiple `NULL` values cleanly without needing a partial `WHERE IS NOT NULL` predicate, satisfying both Drizzle `.onConflictDoUpdate({ target })` and nullable manual rows).
- Test to add: Migration integration test running `drizzle-kit migrate` on an empty Postgres database followed by executing `syncRealWhatsappGroups` twice (initial insert + idempotent conflict update) and inserting two `NULL`-handle manual channels.

- Confidence: High
- Needs owner decision: no

### A15-004 — `purgeFakeMarketingChannelsAction` wipes Core 5 social channels & `deleteLinkedDeviceSessionSlotAction` cascades chat deletion
- Severity: P0
- Category: data-integrity
- Where: `web/app/actions/whatsapp-linked-device.ts:198-219, 352-399`, `web/lib/whatsapp/linked-device.ts:104-125`, `web/db/schema/whatsapp-crm.ts:276-278, 344-346`
- Brief claim contradicted (if any): Code docblock at `whatsapp-linked-device.ts:353-355` claims `purgeFakeMarketingChannelsAction` only *"Purges fake / seeded placeholder WhatsApp channels"*, and `L200` claims `deleteLinkedDeviceSessionSlotAction` *"Rejects deletion of 'default' and 'secondary' — use Disconnect instead"*.
- Evidence: (1) In `app/actions/whatsapp-linked-device.ts:358-367`, `purgeFakeMarketingChannelsAction` selects from `marketingChannels` using `or(isNull(marketingChannels.externalGroupIdOrHandle), and(notLike(marketingChannels.externalGroupIdOrHandle, "%@g.us"), notLike(marketingChannels.externalGroupIdOrHandle, "status@broadcast%")))` **with zero `WHERE platform IN ('whatsapp_group', 'whatsapp_community', 'whatsapp_status')` filter** (`A00-002`). Because Instagram (`@alramlahtravels`), Facebook Page IDs, TikTok handles, YouTube channel IDs, and Google Business Profile IDs do not end in `@g.us` or start with `status@broadcast`, `L379-388` deletes **100% of Core 5 social `marketing_channels` rows and their historical `daily_post_distributions`**. (2) In `deleteLinkedDeviceSessionSlot` (`linked-device.ts:104-125`), despite the comment at `whatsapp-linked-device.ts:200`, neither `deleteLinkedDeviceSessionSlotSchema` (`validations/whatsapp-linked-device.ts:29-31`) nor `deleteLinkedDeviceSessionSlot` blocks `"default"` or `"secondary"`, AND `L118-120` deletes `whatsapp_accounts` where `phoneNumberId = "linked-${sessionKey}"`—which triggers `onDelete: "cascade"` on `whatsapp_conversations` (`db/schema/whatsapp-crm.ts:278`) and `whatsapp_messages` (`L346`), permanently destroying every customer chat and message recorded on that phone line!
- Impact (business terms): Clicking purge (or calling the exposed `"use server"` action as any `staff` account) wipes all non-WhatsApp marketing channels and post attribution history across the agency, while removing a linked-device slot silently destroys historical pilgrim WhatsApp conversations in the Desk CRM.
