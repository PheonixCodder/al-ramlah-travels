### A16-001 — Unauthenticated `executeScheduledPostNowAction` Server Action permits anonymous publishing
- Severity: P0
- Category: security
- Where: `web/app/actions/social-scheduler.ts:1443-1662`
- Brief claim contradicted (if any): `AGENTS.md` Rule ("Validate every Server Action, Route Handler, and form payload with `zod`" and admin-authenticated server mutations).
- Evidence: `web/app/actions/social-scheduler.ts:1` declares `"use server"` at module top, making every exported `async function` a publicly reachable Next.js Server Action HTTP endpoint. Every other exported action in the file calls `await requireAdmin()` (e.g., lines `272`, `362`, `540`, `577`, `687`, `1027`, `1677`, `1739`, `1780`), whereas `export async function executeScheduledPostNowAction(params: { scheduledPostId: string })` at lines `1443-1457` performs **zero authentication check** (`requireAdmin()` is absent because the author assumed Trigger.dev was the only caller, even though Trigger runs on a separate worker via direct TypeScript import at `trigger/publish-social-post.task.ts:34` rather than Server Action RPC) and **zero Zod UUID validation**, passing `params.scheduledPostId` directly to Drizzle `eq(scheduledPosts.id, params.scheduledPostId)` and returning differentiated responses (`"Scheduled post <id> not found"` vs `{ success: true, postStatus: "completed" }`).
- Impact (business terms): Any unauthenticated internet attacker who extracts or guesses the Next-Action ID from the client bundle can force premature live publication of scheduled/draft agency campaigns across connected Meta, TikTok, YouTube, and Google Business accounts, re-trigger failed targets, and probe UUID existence without logging in.
- Root cause: Internal worker orchestration helper was exported directly from a `"use server"` module instead of an internal server-only service module (`lib/social/publish-executor.ts`), omitting both `requireAdmin()` and `z.object({ scheduledPostId: z.string().uuid() })`.
- Recommended fix: Move the raw execution function (`executeScheduledPostNowInternal`) into `import "server-only"` module `web/lib/social/publish-executor.ts` for `trigger/publish-social-post.task.ts` and `createScheduledSocialPostAction` to import directly; if a UI-callable Server Action wrapper remains in `app/actions/social-scheduler.ts`, gate it with `await requireAdmin()` and `z.object({ scheduledPostId: z.string().uuid() }).parse(params)`.
- Test to add: Unit test in `web/app/actions/__tests__/social-scheduler-auth.test.ts` mocking `requireAdmin` to throw `Unauthorized` and asserting every exported function in `app/actions/social-scheduler.ts` rejects unauthenticated calls before touching `db`.
- Effort: S (<2h)
- Confidence: High
- Needs owner decision: no

### A16-002 — Arbitrary local file read (`fs.readFile`), unfettered SSRF, and video RAM OOM in media loaders
- Severity: P0
- Category: security
- Where: `web/lib/social/providers/facebook.ts:73-88,344-354,486-496`, `web/lib/social/providers/youtube.ts:67-82,285,339`, `web/lib/social/normalize-media.ts:26-50`
- Brief claim contradicted (if any): Safe Cloudflare R2 media ingestion and durable worker stability under `socialPublishQueue` (`concurrencyLimit: 5`).
- Evidence: All three media-loading functions (`fetchVideoBytes` in `facebook.ts:73-88` & `youtube.ts:67-82`, and `loadSourceImageBytes` in `normalize-media.ts:26-50`) follow the same unsafe pattern: (1) if `url` starts with `http://` or `https://`, they execute `await fetch(url)` with **zero hostname/IP allowlist or private-CIDR blocklist** (`127.0.0.1`, `169.254.169.254`, Oracle Gotenberg internal host), **zero `AbortSignal.timeout`**, and **zero `Content-Length` / stream byte limit**; (2) otherwise, if a payload passes a relative path (note `facebook.ts` / `youtube.ts` adapters and `executeScheduledPostNowAction` accept DB `mediaUrls` directly and `campaigns-hub-client.tsx:1677` lets staff append arbitrary strings before submit; while `createScheduledPostSchema` checks `.url()`, `file:///...` or internal callers bypass HTTP), `const cleanPath = videoUrl.startsWith("/") ? videoUrl.slice(1) : videoUrl; const localFilePath = path.join(process.cwd(), "public", cleanPath); return await fs.readFile(localFilePath)` executes **with zero `path.resolve` prefix check**, allowing `../../.env` traversal; and (3) `facebook.ts:344-354,486-496` and `youtube.ts:285,339` hold both `Buffer.from(await res.arrayBuffer())` AND `new Uint8Array(videoBuffer)` in heap simultaneously, so 5 concurrent 250 MB Reel/Short uploads (`socialPublishQueue` `concurrencyLimit: 5` in `trigger/publish-social-post.task.ts:43`) allocate `>2.5 GB` and OOM-crash the Next.js / Trigger worker.
- Impact (business terms): An authenticated staff account (or an unauthenticated caller chaining `A16-001` against existing DB records) can induce SSRF against cloud metadata / localhost services or crash the production publishing worker with a single large 4K video upload.
- Root cause: Raw `fetch()` and `fs.readFile()` helpers were duplicated across 3 files without URL origin allowlisting (strictly `R2_PUBLIC_URL` + `NEXT_PUBLIC_APP_URL/uploads/`), `path.resolve` containment checks, byte caps, or streaming uploads.
- Recommended fix: Centralize media retrieval into a single `lib/social/safe-media-reader.ts` that (a) strictly allowlists `https:` URLs under `env.R2_PUBLIC_URL` (blocking RFC1918/link-local/loopback resolved IPs), (b) enforces `path.resolve(publicUploadsRoot, rel).startsWith(publicUploadsRoot + path.sep)` for dev local uploads, and (c) streams R2 object bodies (`ReadableStream` + `Content-Length` cap `<=250 MB` with `AbortSignal.timeout(60_000)`) into Meta/YouTube resumable upload endpoints instead of double-buffering `ArrayBuffer` + `Buffer` in RAM.
- Test to add: Unit tests in `web/lib/social/__tests__/safe-media-reader.test.ts` asserting rejection of `http://169.254.169.254/latest/meta-data/`, `http://127.0.0.1:3001`, `../../.env`, and responses exceeding the byte limit.
- Effort: M (<1d)
- Confidence: High
- Needs owner decision: no

### A16-003 — 6-hour Meta token refresh overwrites Facebook/Instagram Page Access Tokens with User tokens
- Severity: P0
- Category: functional
- Where: `web/lib/social/token-refresh.ts:122-151`, `web/trigger/schedules.task.ts:141-172,298-305`, `web/lib/social/providers/facebook.ts:188-189,217-250`, `web/lib/social/providers/instagram.ts:354-355,384-417`, `web/app/actions/social-scheduler.ts:1294-1319`
- Brief claim contradicted (if any): `AGENTS.md` ("proactive token refresh" keeping Core 5 Facebook Pages & Instagram Business accounts continuously publishable).
- Evidence: During initial OAuth (`facebook.ts:188-189`, `instagram.ts:354-355`), `accessToken` is set to `page.access_token` (a **Facebook Page Access Token**) while `refreshToken` is set to `longLivedUserToken` (a 60-day **User Access Token**). However, `facebookProvider.refreshAccessToken(refreshToken)` (`facebook.ts:217-250`) and `instagramProvider.refreshAccessToken(refreshToken)` (`instagram.ts:384-417`) call `GET /oauth/access_token?grant_type=fb_exchange_token&fb_exchange_token=${refreshToken}`, which returns a refreshed **User Access Token** (`data.access_token`), and return `{ accessToken: data.access_token, refreshToken: data.access_token }`. Both `refreshSingleSocialIntegration` (`lib/social/token-refresh.ts:142`) and the 6-hour cron `proactiveSocialTokenRefreshTask` (`trigger/schedules.task.ts:154,298-305`, running `0 */6 * * *` with `withinHours: 168`, plus `facebook`/`instagram` unconditionally included even when `tokenExpiresAt` is null at `schedules.task.ts:132-135` and `token-refresh.ts:75-78`) write `encryptedAccessToken = encryptSocialToken(refreshed.accessToken)` directly into `social_integrations.encrypted_access_token` without ever calling `GET /{pageId}?fields=access_token` (or `/me/accounts`) to derive a Page Access Token, while leaving `metadata.encryptedPageAccessToken` untouched. On Meta Graph API `v25.0`, `POST /{page-id}/feed`, `/{page-id}/photos`, `/{page-id}/video_reels`, and `/{page-id}/photo_stories` **require a Page Access Token** and reject a User Access Token with `OAuthException (#190 / #200): This endpoint requires a Page access token`.
- Impact (business terms): Every connected Facebook Page (and Page-token-backed Instagram Business integration) works immediately after OAuth connection and then **permanently breaks at the next 6-hour cron tick** (at `00:00`, `06:00`, `12:00`, or `18:00 UTC` once within the refresh window, or immediately when an admin clicks `"Refresh Token"` / `"Sweep Expiring"` in `/admin/settings`), halting scheduled social campaigns until an admin manually disconnects and reconnects OAuth.
- Root cause: `facebookProvider.refreshAccessToken` and `instagramProvider.refreshAccessToken` treat `fb_exchange_token`'s returned User token as a drop-in replacement for `encryptedAccessToken` (which stores a Page token) and lack `internalAccountId` / `pageId` context to re-fetch the Page Access Token (note: a Page token derived from a long-lived User token already has `expires_at = 0` / never-expiring lifetime on Meta!).
- Recommended fix: Pass integration context (`internalAccountId` and `metadata.pageId`) into `refreshAccessToken`: after exchanging `fb_exchange_token` for a fresh long-lived User token, store the User token in `encryptedRefreshToken` ONLY, then fetch `GET https://graph.facebook.com/v25.0/${pageId}?fields=access_token` using that User token to obtain the never-expiring Page Access Token for `encryptedAccessToken` (and update `metadata.encryptedPageAccessToken` in sync).
- Test to add: Unit test in `web/lib/social/__tests__/token-refresh-meta.test.ts` mocking Graph `/oauth/access_token` (`USER_TOK_2`) and `/{pageId}?fields=access_token` (`PAGE_TOK_2`), asserting `encryptedAccessToken` decrypts to `PAGE_TOK_2` (never `USER_TOK_2`) and `encryptedRefreshToken` decrypts to `USER_TOK_2`.
- Effort: S (<2h)
- Confidence: High
- Needs owner decision: no

### A16-004 — Google Business Profile calls sunset `mybusiness.googleapis.com/v4` endpoints (`HTTP 404`) and fabricates `ACTIVE` OAuth accounts on `403`/`429`
- Severity: P0
- Category: functional
- Where: `web/lib/social/providers/gmb.ts:136-204,403,446`, `web/lib/social/analytics.ts:287`
- Brief claim contradicted (if any): `AGENTS.md` & `01-feature-parity.md` ("Core 5 OAuth & publishing: Instagram, Facebook Pages, TikTok, YouTube, Google Business Profile" + Cross-Channel Analytics).
- Evidence: (1) `gmb.ts:446` and `lib/social/analytics.ts:287` call `POST https://mybusiness.googleapis.com/v4/${locationPath}/localPosts:reportInsights` — Google **sunset and shut down** v4 `reportInsights` in favor of the **Business Profile Performance API v1** (`https://businessprofileperformance.googleapis.com/v1/locations/{locationId}:fetchMultiDailyMetricsTimeSeries`), so metrics calls return `HTTP 404` 100% of the time; (2) `gmb.ts:403` calls `POST https://mybusiness.googleapis.com/v4/${locationPath}/localPosts`, which requires explicit Google Business Profile API Partner/Basic Access approval (default Google Cloud projects have **0 QPM quota** on `mybusiness*` APIs) AND a valid `accounts/{accountId}/locations/{locationId}` resource path; and (3) when OAuth hits that default `403`/`429` quota wall at `gmb.ts:136-204`, `exchangeCodeForTokens` **catches the failure and fabricates a fake candidate** with `internalAccountId: "gmb_pending_quota"` (`L147`) or `"accounts/${userInfo.sub || 'default'}/locations/primary"` (`L197`), which `callback/route.ts:154-175` inserts into `social_integrations` with `status: "ACTIVE"` and `isActive: true`! When a post is later scheduled to that `"ACTIVE"` GMB row, `gmb.ts:336-354` resolves `locationPath = "accounts/gmb_pending_quota/locations/primary"` and hits `/v4/accounts/gmb_pending_quota/locations/primary/localPosts` -> guaranteed `HTTP 404 / 403`.
- Impact (business terms): Admins see a green `"Connected / Active"` badge for Google Business Profile in `/admin/settings` and `/admin/campaigns`, yet 100% of scheduled Google Maps Local Updates fail at publish time, and analytics silently fall back to SHA-256 fake numbers (`A16-007`).
- Root cause: `gmb.ts` relies on unmigrated legacy `mybusiness.googleapis.com/v4` endpoints and masks `403`/`429` unapproved-API errors during OAuth with synthetic placeholder resource IDs marked `ACTIVE`.
- Recommended fix: (1) Never mark `gmb_pending_quota` or synthetic `locations/primary` rows `ACTIVE` — surface a clear OAuth error banner instructing the owner to complete Google's GBP API Basic Access request (`§11.11`); (2) migrate GBP insights from `v4/.../localPosts:reportInsights` to `businessprofileperformance.googleapis.com/v1/locations/{locationId}:fetchMultiDailyMetricsTimeSeries`; and (3) verify `accounts/{accountId}/locations/{locationId}` discovery via `mybusinessaccountmanagement.googleapis.com/v1/accounts` + `mybusinessbusinessinformation.googleapis.com/v1/{account}/locations` only persists real Google location IDs.
- Test to add: Unit test in `web/lib/social/providers/__tests__/gmb.test.ts` verifying `exchangeCodeForTokens` throws a descriptive quota-approval error on `403`/`429` instead of returning `"gmb_pending_quota"`, and verifying analytics hits `businessprofileperformance.googleapis.com/v1`.
- Effort: M (<1d)
- Confidence: High
- Needs owner decision: yes

### A16-005 — Instagram skips container polling on single `REEL`/`STORY`/video & carousel parent, misses OAuth scopes, and violates `4:5` (`0.80`) Feed ratio
- Severity: P0
- Category: functional
- Where: `web/lib/social/providers/instagram.ts:20-26,474-516,572-598,683,742`, `web/lib/social/normalize-media.ts:11-12`, `web/app/actions/social-scheduler.ts:1064-1082`

### A16-006 — `wait.until` vs 5-minute sweeper double-publish race and swallowed errors breaking Trigger retries & 2-step funnels
- Severity: P0
- Category: reliability
- Where: `web/trigger/publish-social-post.task.ts:219-289,383-465`, `web/app/actions/social-scheduler.ts:1176,1472-1486,1528-1649`
- Brief claim contradicted (if any): `AGENTS.md` ("Global Idempotency Key scoping via `idempotencyKeys.create(key, { scope: 'global' })`" and reliable 2-Step Spotlight-then-Sheet publishing).
- Evidence: Three orchestration bugs interact in `publish-social-post.task.ts` and `social-scheduler.ts`: (1) **Sweeper vs `wait.until` duplicate publish race**: when a post is scheduled for `T` (e.g. `11:00:00 PKT`), `createScheduledSocialPostAction` (`social-scheduler.ts:1176`) triggers `publish-social-post` with idempotency key `soc-post-run-${postId}`, which sleeps at `await wait.until({ date: targetTime })` (`publish-social-post.task.ts:238`) while `scheduled_posts.status` remains `"scheduled"`. ## What Works

- **AES-256-GCM Token Vault (`web/lib/social/crypto.ts:19-99`)**: Uses `crypto.scryptSync` key derivation, fresh random 16-byte IV per encryption, 16-byte GCM auth tag integrity verification, and hard-throws in `NODE_ENV === "production"` if `ENCRYPTION_KEY` is missing or `< 16` chars (`L24-30`), while `toSafeIntegration` (`app/actions/social-scheduler.ts:154-199`) strips `encryptedAccessToken`, `encryptedRefreshToken`, and `metadata.oauthCandidates` before returning integration rows to React clients.
- **OAuth PKCE S256 & Constant-Time CSRF State Check (`web/app/api/oauth/social/[provider]/route.ts:62-75,115-167`, `callback/route.ts:95-115`)**: Generates 32-byte CSPRNG `state` and 48-byte PKCE `code_verifier` (`S256` SHA-256 challenge for TikTok & YouTube), stores them in `HttpOnly; SameSite=Lax` 10-minute cookies, and compares `state` via `crypto.timingSafeEqual` after length verification.
- **Progressive mozjpeg Normalizer (`web/lib/social/normalize-media.ts:56-91`)**: Uses `sharp` with EXIF `.rotate()`, `fit: "contain"` Warm Ivory `#FAF7F2` luxury letterboxing (never cropping package pricing tables at flyer edges), and `{ quality: 90, progressive: true, mozjpeg: true }` output.
- **WhatsApp First-Comment Builder & Analytics Rollup Math (`web/lib/social/first-comment.ts:27-80`, `web/lib/social/analytics-aggregate.ts:96-231`)**: `buildArtFirstCommentPlug` cleanly normalizes Pakistani `03...` numbers to `923...` `wa.me` deep links with URL-encoded `ART-...` package codes (`A14`/Package Bot compatible) and PKR price formatting, while `aggregateCampaignAnalytics` is a clean, pure, zero-division-safe rollup across Core 5 providers with ranked top-post attribution.
- **PKT Slot Formatting Primitives (`web/lib/social/time-slots.ts:43-116`)**: `formatPktDateKey` and `parsePktSlotToUtc` accurately model Pakistan Standard Time (`UTC+05:00`, no DST since 2009) and enforce peak `11:00`, `16:00`, and `21:00 PKT` windows with `minLeadMinutes` lead-time filtering.
