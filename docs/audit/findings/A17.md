## Detailed Findings

### A17-001 — `dispatchViaWhatsAppBridge` sends unsupported `@g.us` / `status@broadcast` / cold free-form payloads to Meta Cloud API and fabricates `"sent"` DB records on error
- Severity: P0
- Category: data-integrity
- Where: `web/lib/bridges/marketing-bridges.ts:146-263`, `web/lib/whatsapp/meta-api.ts:122-146, 446-490`, `web/app/actions/marketing-ops.ts:1304-1360, 1489-1523`, `web/tests/trigger-v4-webhook-and-realtime-copilot.test.ts:460-488`
- Brief claim contradicted (if any): §6.4 "WhatsApp Group, Community & Status Queue (Safe Human-in-the-Loop Distribution)"
- Evidence:
  1. `dispatchOrLogDistribution` (`web/app/actions/marketing-ops.ts:1304-1325`) calls `dispatchViaWhatsAppBridge` whenever `dispatchMode === "auto_bridge"` for `whatsapp_group`, `whatsapp_community`, or `whatsapp_status` channels, and `sendPersonalOutreachAction` (`marketing-ops.ts:1489-1496`) calls it in `direct_1on1` mode.
  2. `dispatchViaWhatsAppBridge` (`web/lib/bridges/marketing-bridges.ts:207`) initializes `let wamid = \`wamid.bridge_${Date.now()}_...\`` before calling `sendWhatsAppImageMessage` (`L216`) or `sendWhatsAppTextMessage` (`L229`), both of which POST to `https://graph.facebook.com/v21.0/${phoneNumberId}/messages` (`web/lib/whatsapp/meta-api.ts:446-490`) using `recipientFields(to)` (`meta-api.ts:137-146`), which hardcodes `recipient_type: "individual"` and strips all non-digits via `sanitizePhoneForMeta(trimmed)` (`meta-api.ts:122-135`):
     - **Group (`120363...@g.us`)**: Meta Cloud API does not support consumer WhatsApp Groups or Communities; `sanitizePhoneForMeta` strips `@g.us` and sends `to: "120363..."` as an individual E.164 phone number -> Graph API rejects with HTTP `400` (`#131030` recipient not in allowed/valid phone format).
     - **Status (`status@broadcast` / `status@broadcast:default` or channel name fallback `ch.externalGroupIdOrHandle || ch.name` at `marketing-ops.ts:1318`)**: Meta Cloud API has no WhatsApp Status endpoint; `sanitizePhoneForMeta` strips all letters/symbols to `to: ""` -> Graph API rejects with HTTP `400` (`#100 Invalid parameter`).
     - **Cold `direct_1on1` VIP Outreach (`marketing-ops.ts:1490`)**: Sends a free-form `image` or `text` message (not an approved HSM template) to a prospect who has not messaged within 24 hours -> Graph API rejects with HTTP `400` (`#131047 Re-engagement message`). In addition, `marketing-bridges.ts:209-213` catches `decrypt()` failures and passes raw AES-GCM ciphertext (`wabaAccount.encryptedAccessToken || "mock_offline_token"`) as the Bearer token.
  3. **Silent production fabrication**: Both Graph API calls wrap errors in empty `catch { // simulation wamid retained on offline dev }` blocks (`marketing-bridges.ts:225-227, 237-239`) with **no `NODE_ENV` guard**. On every Graph API rejection in production, execution continues to `L242-262`, inserting a bogus `whatsappConversations` row (creating fake inbox threads with `contactPhone = "120363...@g.us"` or `"status@broadcast:default"` in `/admin/desk`) and a bogus `whatsappMessages` row (`wamid: "wamid.bridge_..."`, `status: "sent"`), returning `dispatched: true`. Callers then record `daily_post_distributions.status = "sent"` (`marketing-ops.ts:1324, 1349`) or lock the VIP contact for 14 days with `outreach_logs.delivery_status = "sent"` (`marketing-ops.ts:1503-1523`). Worse, `web/tests/trigger-v4-webhook-and-realtime-copilot.test.ts:460-488` asserts `assert.equal(res.dispatched, true)` for `@g.us`, enshrining the fake success in CI.
- Impact (business terms): Staff and management see green `"sent"` logs, fake outbound messages in the Live WhatsApp Desk Inbox, and locked 14-day VIP outreach records when **zero** posters or messages ever reached any WhatsApp Group, Status, or VIP pilgrim.
- Root cause: Prototype simulation fallbacks (`wamid.bridge_*` and empty `catch {}` blocks) were left unconditionally active in production code on top of an invalid assumption that Meta WhatsApp Cloud API `/messages` can post to consumer `@g.us` groups, `status@broadcast`, and cold 1-on-1 contacts without templates.
- Recommended fix:
  1. Remove `@g.us` group and `status@broadcast` modes from `dispatchViaWhatsAppBridge` entirely — reject them with a typed error directing callers to either the human-in-the-loop assisted queue or an isolated Linked-Device sidecar (per owner decision §11.1).
  2. Delete `wamid.bridge_*`, `"mock_offline_token"`, raw-ciphertext token fallback, and empty `catch {}` blocks in `web/lib/bridges/marketing-bridges.ts:205-263`; propagate real Meta errors (`dispatched: false`) so `sendPersonalOutreachAction` does not lock `cooldownUntil` or log `"sent"` when delivery fails.
  3. For 1-on-1 VIP outreach (`Needs owner decision` below), owner must choose between: (a) sending an **approved Meta utility/marketing template** via Cloud API, (b) pure **human-assisted `wa.me` click-to-chat** (logging `"manual_logged"` only after staff confirmation), or (c) an isolated **Baileys sidecar** (`SWARM_PROMPT.md` §11.1).
- Test to add: Unit/integration test in `web/tests/marketing-bridges.test.ts` asserting `dispatchViaWhatsAppBridge` rejects `@g.us` and `status@broadcast` inputs (`dispatched: false`), propagates Meta HTTP `400`/`#131047` errors without inserting `whatsapp_conversations` or `whatsapp_messages` rows, and leaves `outreach_contacts.cooldown_until` untouched on failure.
- Effort: M (<1d)
- Confidence: High
- Needs owner decision: yes

### A17-002 — Inbound `"STOP"` / `"UNSUBSCRIBE"` opt-out replies unlock the 14-day cooldown instead of setting `do_not_contact`
- Severity: P0
- Category: compliance
- Where: `web/app/api/webhooks/whatsapp/route.ts:615-621`, `web/lib/whatsapp/post-ref-detector.ts:116-164`, `web/lib/domain/marketing-ops.ts:200-217`, `web/lib/whatsapp/intake-flow.ts:238-240`, `web/app/(public)/privacy/page.tsx:111-112`
- Brief claim contradicted (if any): §5.4 #9 "14-day cooldown per phone number unless customer replies"
- Evidence:
  1. Public Privacy Policy §4 (`web/app/(public)/privacy/page.tsx:111-112`) explicitly promises pilgrims: *"Reply 'STOP' at any time on WhatsApp to opt out of promotional broadcasts and 14-day VIP outreach messages."*
  2. In `web/app/api/webhooks/whatsapp/route.ts:620-621`, **every** inbound webhook event unconditionally invokes `await unlockOutreachCooldownForPhone(senderPhone)` regardless of message text or type (even `"STOP"`, `"UNSUBSCRIBE"`, `"REMOVE"`, `"MAT BHEJO"`, or removing an emoji reaction at `L615`).
  3. `unlockOutreachCooldownForPhone` (`web/lib/whatsapp/post-ref-detector.ts:144-158`) checks `shouldUpdateStatus` so `interestStatus` stays unchanged if already `"do_not_contact"`, **but still unconditionally writes `lastInboundReplyAt: now` (`L153`) on every matched contact** — and for any `"prospect"` or `"replied_active"` contact who texts `"STOP"`, sets `interestStatus: "replied_active"` AND `lastInboundReplyAt: now`!
  4. `calculateOutreachCooldown` (`web/lib/domain/marketing-ops.ts:200-217`) checks `if (lastReply.getTime() > lastOut.getTime()) return { isLocked: false, isExemptActiveReply: true, isEligibleToMessage: true }` without inspecting `interestStatus`. Meanwhile `evaluateIntakeTransition` (`web/lib/whatsapp/intake-flow.ts:238-240`) handles `lower === "stop"` only by resetting the 3-step intake conversation to `"IDLE"` without updating `outreach_contacts`.
  5. Result: A locked VIP contact (or even an existing `"do_not_contact"` row) who replies `"STOP"` immediately **unlocks** their 14-day cooldown and jumps into `"Today's Eligible Outreach Queue"` as `"Unlocked (Customer Replied — Active Conversation)"` (`marketing-ops.ts:214`)!
- Impact (business terms): Direct breach of Al Ramlah Travels' published `/privacy` commitment, Pakistan PECA electronic-messaging consent rules, and Meta WhatsApp Business Policy — pilgrims demanding `"STOP"` are promoted to top-priority outreach targets, triggering spam reports and permanent WABA number bans.
- Root cause: Inbound webhook processing equates *any* inbound webhook packet with positive commercial engagement (`unlockOutreachCooldownForPhone`) and lacks an opt-out keyword interceptor (`STOP`, `UNSUBSCRIBE`, `OPT OUT`, `BLOCK`, `MAT BHEJO`) prior to cooldown evaluation.
- Recommended fix:
  1. Add a shared `isWhatsAppOptOutMessage(text)` helper matching normalized opt-out keywords (`stop`, `unsubscribe`, `opt out`, `optout`, `remove`, `cancelpromo`, `mat bhejo`) and ignore non-message reactions (`msg.type === "reaction"`).
  2. In both `web/app/api/webhooks/whatsapp/route.ts` and `web/lib/whatsapp/linked-device.ts` inbound handlers: when `isWhatsAppOptOutMessage(textContent)` is true, atomically upsert/update `outreach_contacts` (`interestStatus = "do_not_contact"`, `doNotContactAt = now`), skip `unlockOutreachCooldownForPhone`, cancel any active intake flow, and send a single Meta-compliant opt-out confirmation message.
  3. In `unlockOutreachCooldownForPhone` (`post-ref-detector.ts:144`), immediately `continue` without updating `lastInboundReplyAt` whenever `contact.interestStatus === "do_not_contact"`.
- Test to add: Integration test simulating inbound webhook payload `{ type: "text", text: { body: "STOP" } }` from a locked contact in `outreach_contacts`: assert `interestStatus === "do_not_contact"`, `computeOutreachCooldownState(...).isEligibleToMessage === false`, and reaction events do not unlock cooldown.
- Effort: M (<1d)
- Confidence: High
- Needs owner decision: no

### A17-003 — `do_not_contact` and 14-day VIP cooldown are bypassed across VIP Outreach, Meta Broadcasts, Desk sends, and Linked-Device paths, with zero UI or Server Action to set `do_not_contact`
- Severity: P0
- Category: compliance
- Where: `web/lib/domain/marketing-ops.ts:174-268`, `web/app/actions/marketing-ops.ts:1380-1541`, `web/lib/validations/marketing.ts:107-118`, `web/components/admin/marketing/outreach-client.tsx:111-135`, `web/db/schema/suppliers-and-marketing.ts:80-89, 417-419`, `web/app/actions/whatsapp-crm.ts:653-1024, 1127-1382, 1710-2014`, `web/lib/whatsapp/linked-device.ts:424-521, 827-893`, `web/app/api/webhooks/whatsapp/route.ts:297-368`
- Brief claim contradicted (if any): §6.4 "Strict 14-day cooldown per phone number (automatically unlocked if customer replies)."
- Evidence:
  1. **Zero way to set `do_not_contact` + untyped column**: `contactLeadStatusEnum` (`web/db/schema/suppliers-and-marketing.ts:80-89`) defines `"do_not_contact"`, but `outreachContacts.interestStatus` (`L417-419`) uses raw `varchar("interest_status", { length: 32 })` instead of the enum, and both `outreachContactSchema` (`web/lib/validations/marketing.ts:107-118`) and `upsertOutreachContact` (`web/app/actions/marketing-ops.ts:1380-1438`) omit `interestStatus`. Repo-wide search confirms **0 writes** of `"do_not_contact"` anywhere in `web/`.
  2. **VIP Outreach ignores `do_not_contact`**: Neither `computeOutreachCooldownState` (`web/lib/domain/marketing-ops.ts:253-268`), nor `OutreachClient` (`web/components/admin/marketing/outreach-client.tsx:111-135`), nor `sendPersonalOutreachAction` (`web/app/actions/marketing-ops.ts:1461-1472`) checks `contact.interestStatus === "do_not_contact"`. A `"do_not_contact"` row renders in `"Today's Eligible Outreach Queue"` with an active `"Send Package & Lock 14 Days"` button and dispatches without error.
  3. **Meta Broadcasts bypass both server-side `do_not_contact` and 14-day cooldown, and never update `lastOutreachAt`**:
     - In `campaigns-hub-client.tsx:4266-4281`, `all_vip` and `askari_dha` segments filter `do_not_contact` in client JS **but ignore the 14-day cooldown**, targeting VIPs who were already messaged yesterday; `custom_phones` / CSV uploads (`L4256-4264`) filter **neither** `do_not_contact` nor cooldown.
     - `createAndQueueWhatsappBroadcastAction` (`web/app/actions/whatsapp-crm.ts:1163-1210`) performs **zero server-side lookup** against `outreach_contacts` to exclude `do_not_contact` or locked numbers, and `send-whatsapp-broadcast.task.ts:344-426` **never updates `outreach_contacts.last_outreach_at` / `cooldown_until` or inserts `outreach_logs`** (and `whatsappBroadcastRecipients.outreachContactId` at `db/schema/whatsapp-crm.ts:347` is never populated).
  4. **Desk manual sends & Linked-Device paths disconnected from cooldown & reply unlock**:
     - `sendWhatsappDeskReplyAction`, `sendWhatsappTemplateMessageAction`, `sendWhatsappInteractiveReplyAction`, and `sendQuotationLuxuryPdfToWhatsappAction` (`whatsapp-crm.ts:653-1024, 1710-2014`) neither check `do_not_contact`/cooldown nor update `lastOutreachAt`/`outreach_logs` on cold template initiation.
     - Linked-Device outbound sends and mobile `smb_message_echoes` (`linked-device.ts:442-521, 827-893`, `webhooks/whatsapp/route.ts:297-368`) never update `lastOutreachAt`/`outreach_logs`. Conversely, **inbound** pilgrim replies received via Baileys Linked Device (`linked-device.ts:424-521`) never call `unlockOutreachCooldownForPhone`, leaving responsive VIP pilgrims falsely locked for 14 days!
- Impact (business terms): Invariant #9 (`H31`) is enforced only inside a single button of `/admin/campaigns?tab=outreach` — staff can unknowingly spam a VIP pilgrim via a Meta CSV broadcast at 10 AM, a cold Desk template at 2 PM, and a 1-on-1 VIP Outreach card at 4 PM on the same day, while opted-out contacts cannot even be flagged or suppressed.
- Root cause: Cooldown and suppression state (`outreach_contacts`) was built as an isolated silo for `sendPersonalOutreachAction` rather than a centralized phone-level compliance gate shared across `marketing-ops.ts`, `whatsapp-crm.ts`, `send-whatsapp-broadcast.task.ts`, and `linked-device.ts`.
- Recommended fix:
  1. Migrate `outreachContacts.interestStatus` to `contactLeadStatusEnum` (plus explicit `doNotContact: boolean("do_not_contact").notNull().default(false)`), expose a `"Do Not Contact"` toggle in `OutreachClient` and Desk Inbox, and pass `interestStatus` / `doNotContact` into `calculateOutreachCooldown` so `doNotContact === true` always returns `{ isLocked: true, isEligibleToMessage: false }`.
  2. Enforce a centralized server-side `assertAndRecordOutboundMarketingTouch()` helper inside `sendPersonalOutreachAction`, `createAndQueueWhatsappBroadcastAction` / `send-whatsapp-broadcast.task.ts` (suppressing `do_not_contact` + 14-day locked phones across CSV/segments and updating `lastOutreachAt`, `cooldownUntil`, and `outreach_logs` on `MARKETING` template delivery), cold Desk template sends, and Linked-Device outbound sends.
  3. Call `unlockOutreachCooldownForPhone(contactPhone)` inside `linked-device.ts` (`!isFromMe` inbound path) after checking `!isWhatsAppOptOutMessage(text)`.
- Test to add: Cross-channel compliance suite asserting: (a) a `do_not_contact` phone is rejected/filtered by `sendPersonalOutreachAction`, `createAndQueueWhatsappBroadcastAction` (including CSV upload), and cold Desk template send; (b) sending a `MARKETING` broadcast locks matching `outreach_contacts` for 14 days; (c) an inbound Linked-Device reply unlocks the 14-day cooldown.
- Effort: M (<1d)
- Confidence: High
- Needs owner decision: no
