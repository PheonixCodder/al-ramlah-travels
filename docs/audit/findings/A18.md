### A18-001 — Production Inline Execution Fallback Runs Heavy 60–300s Jobs Inside Short-Lived Vercel Functions (`H1`)
- Severity: P0
- Category: reliability
- Where: `web/trigger/dispatch.ts:42-61`, `web/trigger/dispatch.ts:183-265`, `web/trigger/dispatch.ts:275-362`, `web/trigger/dispatch.ts:384-487`, `web/lib/env.ts:47`, `web/app/actions/quotes.ts:844-899`, `web/app/actions/quoting-copilot.ts:297-342`, `web/app/actions/quoting-copilot.ts:345-410`, `web/app/actions/whatsapp-linked-device.ts:420-450`
- Brief claim contradicted (if any): Brief §9.4 ("Zero-Timeout Operations: AI extraction, Gotenberg rendering, and WhatsApp pacing run outside HTTP lifecycles").
- Evidence: Four distinct dispatch defects defeat Trigger.dev isolation in `NODE_ENV=production`: (1) `TRIGGER_SECRET_KEY` is `.optional()` in `web/lib/env.ts:47`, and `web/trigger/dispatch.ts:42-61` never checks `process.env.NODE_ENV === "production"` — if `TRIGGER_SECRET_KEY` is omitted on Vercel (or accidentally set to a `tr_dev_*` key, which first blocks `2,200ms` on `setTimeout` at `L196, 297, 408`), every task runs inline inside the Vercel function. (2) Even when `TRIGGER_SECRET_KEY=tr_prod_*` **is** configured (`isTriggerProdKeyConfigured() === true`), `triggerByIdBackgroundOrInline` (`L211-216`), `triggerByIdAndAwaitOrInline` (`L319-331`), and `batchTriggerByIdOrInline` (`L424-429`) catch any Trigger API error — **and `triggerByIdAndAwaitOrInline` (`L310-325`) even catches `!finished.isSuccess` when a Cloud run fails or aborts on `AbortTaskRunError`** — and immediately re-run `inlineRunner(payload)` synchronously inside the Vercel HTTP request! (3) Even when Trigger Cloud succeeds, `triggerByIdAndAwaitOrInline` (`L309`, called by `extractSupplierFlyerDraftAction`, `ingestFinishedPosterOrFlyerAction`, `generateMultiPackageSheetForFlyer`, `generateSingleSpotlightForCard`, and `generateApplicationLuxuryPdf`) blocks the Next.js Server Action in an HTTP polling loop (`sdkRuns.poll(handle, { pollIntervalMs: 800 })`) for up to `180–300s`, exceeding Vercel Hobby (`10–60s`) function limits. (4) `startApplicationCopilotRunAction` (`quoting-copilot.ts:390-410`) bypasses Trigger.dev completely (`// Execute directly inline...`), leaving `QuoteWorksheetForm` (`components/admin/applications/quote-worksheet-form.tsx:190-203`) polling `listActiveRunsByTagsAction(["copilot:app:..."])` for a tag never created anywhere in the repo, while `whatsapp-linked-device.ts:441` fires detached `void runSendWhatsappGroupCampaignInline(payload)` which freezes as soon as Vercel flushes the HTTP response.
- Impact (business terms): A missing env var, a transient Trigger.dev API blip, or even a permanently rejected Cloud run causes Vercel serverless functions to execute multi-minute Gotenberg 4K renders, Gemini vision extractions, or 1,000-recipient WhatsApp broadcasts inline — timing out mid-flight, stranding half-written DB rows (`status = "processing"` / `"sending"`), double-charging AI tokens after failed Cloud runs, and freezing detached group campaigns mid-loop.
- Root cause: Development-convenience inline fallbacks (`OrInline` wrappers) were wired unconditionally into production Server Actions and webhook routes without a `NODE_ENV === "production"` fail-fast guard, while synchronous Server Actions used `sdkRuns.poll()` instead of returning `{ runId, publicAccessToken }` to `StudioRealtimeRunBanner` / `CopilotRealtimeRunBanner`.
- Recommended fix: Require `TRIGGER_SECRET_KEY` starting with `tr_prod_` when `NODE_ENV === "production"` in `lib/env.ts`; forbid inline fallback in `dispatch.ts` when `NODE_ENV === "production"` (fail fast with a structured error instead of executing `inlineRunner`, and never re-run inline when `!finished.isSuccess`); convert `triggerByIdAndAwaitOrInline` callers in Studio/Quotes to fire-and-forget `tasks.trigger()` + `useRealtimeRun` (matching `startApplicationLuxuryPdfRunAction`); and wire `startApplicationCopilotRunAction` to `tasks.trigger("quoting-copilot", ...)` with tag `copilot:app:${applicationId}`.
- Test to add: Unit test in `web/tests/trigger-dispatch-prod-guard.test.ts` setting `NODE_ENV="production"` and asserting (a) missing/`tr_dev_*` `TRIGGER_SECRET_KEY` throws immediately without invoking `inlineRunner`, (b) `tasks.trigger` rejection surfaces the error without running `inlineRunner`, and (c) `!finished.isSuccess` never triggers a duplicate inline execution.
- Effort: M (<1d)
- Confidence: High
- Needs owner decision: no

### A18-002 — `throwIfNonRetryable` Without Rethrow & Pervasive `try/catch` Swallowing Disable Trigger.dev Retries Across 7 of 8 `schemaTask`s
- Severity: P0
- Category: reliability
- Where: `web/trigger/errors.ts:293-333`, `web/trigger/extract-packages.task.ts:191-211`, `web/trigger/extract-packages.task.ts:369-379`, `web/trigger/extract-packages.task.ts:459`, `web/trigger/render-gotenberg-asset.task.ts:362-387`, `web/lib/posters/gotenberg.ts:127-176`, `web/trigger/process-inbound-whatsapp.task.ts:146-305`, `web/trigger/mirror-whatsapp-media.task.ts:31-48`, `web/trigger/publish-social-post.task.ts:271-358`, `web/trigger/send-whatsapp-group-campaign.task.ts:91-130`, `web/trigger/quoting-copilot.task.ts:201-210`
- Brief claim contradicted (if any): `AGENTS.md` ("using `schemaTask`, `AbortTaskRunError` error discrimination") and Brief §9.4 ("automatic exponential backoff retries").
- Evidence: `trigger/errors.ts` defines two helpers: `throwIfNonRetryable` (`L293-314`), which throws `AbortTaskRunError` **only** when `!classification.retryable` and returns normally when `retryable === true`, and `rethrowAsTaskError` (`L320-333`), which rethrows transient `Error`s for Trigger.dev backoff — **but `rethrowAsTaskError` has zero callers across the entire codebase**. Consequently: (1) In `extract-packages.task.ts:204-210` and `render-gotenberg-asset.task.ts:380-386`, transient `429`/`502`/`503`/`504`/`ETIMEDOUT` errors pass through `throwIfNonRetryable(err)` without throwing and return `{ success: false, error }`, causing Trigger.dev to mark Attempt 1 `COMPLETED` and skip Attempts 2–3! (2) Worse, in `extract-packages.task.ts:369-379`, if Neon throws a transient connection error during `db.update(supplierFlyers)` or `db.insert(supplierFlyerPackages)`, `catch (dbErr) { throwIfNonRetryable(dbErr) }` returns without throwing and execution proceeds to `L459`, returning `{ success: true, extractedCount: N }` while **zero packages were saved to PostgreSQL**! (3) In `lib/posters/gotenberg.ts:170-176`, any Gotenberg HTTP `503` or `401` is caught and falls back to `renderHtmlViaChromiumCdp`, which throws `"Could not locate Google Chrome..."` (`lib/posters/chromium-cdp.ts:27`) in Cloud, erasing the HTTP status code before `classifyTaskError` sees it. (4) `process-inbound-whatsapp.task.ts` swallows all errors in Stage 1 (`L146`), Stage 2 (`L231`), and Stage 3 (`L289`) and unconditionally returns `{ success: true }` (`L300`); `mirror-whatsapp-media.task.ts:33-47`, `publish-social-post.task.ts:272, 350` (which also ignores Step 2 follow-up failure at `L318-320`), and `send-whatsapp-group-campaign.task.ts:91-130, 241` all return `{ success: false }` instead of throwing; and `quoting-copilot.task.ts:204-209` never classifies OpenRouter `401`/`403` into `AbortTaskRunError`.
- Impact (business terms): Any momentary Oracle Gotenberg restart (`502`/`503`), OpenRouter/Gemini `429` rate limit, Meta CDN `500`, or Neon cold-start timeout permanently fails flyer extraction, 4K poster rendering, social post publishing, and pilgrim passport media archival on the very first attempt — and in `extract-packages`, reports false `"Extraction Complete"` to staff while losing all extracted packages.
- Root cause: Tasks invoke `throwIfNonRetryable` inside `catch` blocks expecting it to handle retryable errors, then return `{ success: false }` payloads instead of calling `rethrowAsTaskError(err)` so Trigger.dev's runtime can observe thrown exceptions and schedule retries.
- Recommended fix: Replace every `throwIfNonRetryable(err); return { success: false }` in `*.task.ts` with `rethrowAsTaskError(err, taskId)` (moving `return { success: false }` exclusively into the local inline wrapper if needed); remove the `renderHtmlViaChromiumCdp` fallback inside `gotenberg.ts` when `NODE_ENV === "production"` or inside Trigger workers so real Gotenberg `4xx`/`5xx` status codes propagate; throw `AbortTaskRunError` on missing DB entities in `send-whatsapp-group-campaign` and `mirror-whatsapp-media`; and rethrow transient stage errors in `process-inbound-whatsapp` while keeping individual stages idempotent via DB flags.
- Test to add: Unit test suite `web/tests/trigger-task-retry-semantics.test.ts` injecting (a) a simulated `503 Service Unavailable` and asserting all 8 task `run` functions **throw** a standard `Error` (triggering retry), (b) a `401 Unauthorized` / `400 Bad Request` and asserting they throw `AbortTaskRunError`, and (c) a DB insert failure in `extract-packages` and asserting it throws rather than returning `success: true`.
- Effort: M (<1d)
- Confidence: High
- Needs owner decision: no
