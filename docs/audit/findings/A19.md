## Detailed Findings

### A19-001 — `isForeignKeyError` is 100% dead code under `DrizzleQueryError`, breaking all 8 soft-delete fallbacks and leaking raw SQL
- Severity: P1
- Category: data-integrity
- Where: `web/app/actions/catalog.ts:32-41,148-167,267-286,371-390,535-554,644-663,729-748`, `web/app/actions/groups.ts:20-29,99-118,229-248`, `web/node_modules/drizzle-orm/errors.js:10-20`, `web/node_modules/drizzle-orm/pg-core/session.js:41,59`
- Brief claim contradicted (if any): Contradicts code docstrings in `catalog.ts:148,267,371,535,644,729` and `groups.ts:99,229` ("If referenced by existing applications ..., falls back to deactivating instead of crashing") and refutes `A04.md` "What Works #5" (`H26`).
- Evidence: `isForeignKeyError(err)` in both `app/actions/catalog.ts:32-41` and `app/actions/groups.ts:20-29` checks `errorObj.code === "23503"` and `errorObj.message.includes("foreign key" | "violates foreign key constraint")` strictly on the top-level `err` object and never inspects `err.cause`. In `drizzle-orm@0.45.2` (`node_modules/drizzle-orm/pg-core/session.js:41,59` and `errors.js:10-20`), every failed Neon/PG query throws `new DrizzleQueryError(query, params, driverError)` where `err.code` is `undefined` and `err.message` is `"Failed query: delete from \"hotels\" where \"hotels\".\"id\" = $1\nparams: <uuid>"`, while PostgreSQL `code: "23503"` and `"violates foreign key constraint"` sit exclusively on `err.cause` (or `err.cause.cause`). Every one of the 8 delete handlers (`deleteHotel`, `deleteVehicle`, `deleteTransportSector`, `deleteZiyaratPlace`, `deleteAirline`, `deleteDepartureCity`, `deleteGroupPackage`, `deleteGroupDeparture`) enters the `else` branch and returns `{ success: false, error: err.message }`, which client handlers (`hotels-client.tsx:100`, `transport-client.tsx:135,169`, `flights-client.tsx:78,108`, `groups-client.tsx:107,139`) display in a raw `window.alert(...)`.
- Impact (business terms): Clicking Delete on any hotel, vehicle, transport sector, airline, departure city, group package, or departure batch that has ever been used in a pilgrim booking or package fails to soft-deactivate the item, leaves outdated inventory live on the public website, and pops a raw browser alert exposing internal SQL table/column names and UUID parameters to staff.
- Root cause: `isForeignKeyError` was written assuming a raw `pg` / `@neondatabase/serverless` `NeonDbError` is thrown directly, without unwrapping Drizzle ORM's `DrizzleQueryError.cause` chain.
- Recommended fix: Implement a shared `unwrapDbError(err)` helper in `lib/db-errors.ts` that walks `err`, `err.cause`, and `err.cause.cause` to check `code === "23503"` (and `"23505"`), sanitize all fallback error messages so `DrizzleQueryError.message` (`Failed query: ...`) is never returned to client components, and replace `window.alert` with structured toast notifications explaining why the item was archived instead of deleted. Also change `visa_rates.updated_by_user_id` (`db/schema/catalog.ts:84`) and `agency_settings.updated_by_user_id` (`db/schema/settings.ts:32`) to `{ onDelete: "set null" }`.
- Test to add: Unit test `isForeignKeyError(new DrizzleQueryError('delete from "hotels" where "id" = $1', ['uuid'], Object.assign(new Error('update or delete on table "hotels" violates foreign key constraint'), { code: '23503' }))) === true`, plus integration tests verifying `deleteHotel` and `deleteGroupDeparture` return `{ action: "deactivated" }` / `{ action: "closed" }` when referenced by an application.
- Effort: S (<2h)
- Confidence: High
- Needs owner decision: no

### A19-002 — Destructive `ON DELETE CASCADE` and missing SQL FKs silently wipe 2D `transport_rates` matrices, `group_departures`, and historical Ziyarat links
- Severity: P1
- Category: data-integrity
- Where: `web/db/schema/catalog.ts:290-295`, `web/db/schema/packages.ts:104-106`, `web/db/schema/applications.ts:163,168-171,300`, `web/db/schema/suppliers-and-marketing.ts:138-140,208-210,260-267,294-296`, `web/app/actions/catalog.ts:267-286,371-390,425-465`, `web/components/admin/catalog/transport-client.tsx:125-138,159-172,188-206`
- Brief claim contradicted (if any): Contradicts `catalog.ts:267,371` ("If referenced by existing applications or transport_rates, falls back to deactivating") and `catalog.ts:535` ("Falls back to deactivating if referenced").
- Evidence:
  1. `transport_rates.sector_id` (`db/schema/catalog.ts:291`) and `transport_rates.vehicle_id` (`L294`) declare `{ onDelete: "cascade" }`. When an admin deletes a vehicle or sector that has no `application_transport_segments` rows yet, PostgreSQL does NOT raise `23503` — it hard-deletes the row and cascades-wipes every custom 2D `transport_rates` cell configured for that vehicle/sector. Meanwhile `TransportClient` (`transport-client.tsx:129,163`) fails to filter `rates` in client state, and `upsertTransportRate` (`transport-client.tsx:192-197` -> `catalog.ts:436,444`) sends only `{ sectorId, vehicleId, rateSar }`, overwriting `ratePkrOverride` and `notes` to `null` on every edit, while `deleteTransportRate` (`catalog.ts:452`) has zero UI button so admins can never reset a `"Custom"` cell back to `"Default"`.
  2. `group_departures.package_id` (`db/schema/packages.ts:105`) declares `{ onDelete: "cascade" }`: deleting a `group_packages` row with 0 `applications` permanently destroys all its scheduled `group_departures` batches and silently nulls `supplier_flyer_packages.published_group_package_id` (`onDelete: "set null"`).
  3. `ziyarat_places` has zero incoming SQL FKs because `applications.selected_ziyarat_place_ids` (`db/schema/applications.ts:168`) is a `jsonb` `string[]`; `deleteZiyaratPlace` (`catalog.ts:538`) always hard-deletes the landmark, silently dropping it from `inArray(schema.ziyaratPlaces.id, application.selectedZiyaratPlaceIds)` on historical dossiers (`applications/[id]/page.tsx:86`).
  4. `applications.supplier_id` (`applications.ts:163`) and `application_quotes.supplier_id` (`L300`) omit `.references(() => suppliers.id)`, while `supplier_flyers`, `supplier_flyer_packages`, and `post_assets` all declare `onDelete: "cascade"` on `suppliers.id`.
- Impact (business terms): Deleting an unused vehicle, sector, group package, or Ziyarat landmark permanently destroys hours of custom 2D SAR matrix pricing, scheduled departure batches, or historical pilgrim Ziyarat selections without warning, and admins cannot clear custom matrix overrides once saved.
- Root cause: Child rate/batch tables were configured with `onDelete: "cascade"` while server action docstrings assumed `NO ACTION` would block deletion, and `selected_ziyarat_place_ids` / `supplier_id` bypassed relational FKs.
- Recommended fix: Change `deleteGroupPackage`, `deleteVehicle`, `deleteTransportSector`, and `deleteZiyaratPlace` to explicitly check child counts (`transport_rates`, `group_departures`, and `sql\`selected_ziyarat_place_ids ? ${id}\`` on `applications`) before executing `db.delete`, archiving (`isActive: false`) whenever referenced; add `.references(() => suppliers.id, { onDelete: "set null" })` on `applications.supplier_id` and `application_quotes.supplier_id`; preserve `ratePkrOverride`/`notes` in `TransportClient` and wire a `"Reset to Default"` button to `deleteTransportRate`.
- Test to add: Integration test creating a `vehicle` + `transport_rates` cell and a `ziyarat_place` referenced in `applications.selectedZiyaratPlaceIds`, calling `deleteVehicle` and `deleteZiyaratPlace`, and asserting both soft-deactivate while preserving the `transport_rates` row and dossier Ziyarat display.
- Effort: M (<1d)
- Confidence: High
- Needs owner decision: no
