### A20-001 — Unsanitized `socialIntegrations.metadata` Serialized into `/admin/settings` RSC Props Leaks Encrypted Candidate OAuth & Page Tokens to All Staff
- Severity: P0
- Category: security
- Where: `web/app/admin/(dashboard)/settings/page.tsx:44`, `web/app/admin/(dashboard)/settings/page.tsx:65-82`, `web/app/admin/(dashboard)/settings/page.tsx:179`, `web/app/api/oauth/social/[provider]/callback/route.ts:155-178`, `web/app/actions/social-scheduler.ts:97-111`
- Brief claim contradicted (if any): `PrivacyPage` (`app/(public)/privacy/page.tsx:131-134`) and `AGENTS.md` claim OAuth access/refresh tokens remain server-side in encrypted storage and are never exposed to client payloads.
- Evidence: During multi-account OAuth discovery (`app/api/oauth/social/[provider]/callback/route.ts:155-178`), when an admin authorizes Facebook, Instagram, YouTube, or Google Business Profile with >1 page/account/location, the callback stores `pendingCandidates` inside `social_integrations.metadata` containing `encryptedAccessToken`, `encryptedRefreshToken`, and `metadata.encryptedPageAccessToken` for every candidate account; after selection (`social-scheduler.ts:439-448`), `metadata.encryptedPageAccessToken` remains on `social_integrations.metadata`. While `listSocialIntegrationsAction` (`social-scheduler.ts:97-111, 290`) explicitly strips both keys via `sanitizeIntegrationMetadata()`, `app/admin/(dashboard)/settings/page.tsx:65-82` queries `metadata: socialIntegrations.metadata` directly from Drizzle and passes `socialRows` straight to `<ConnectionsSettingsClient socialIntegrations={...} />` (`L179`) **without calling `sanitizeIntegrationMetadata()`**, guarded only by `requireAdmin()` (`L44`).
- Impact (business terms): Every `staff` user who opens `/admin/settings` receives the raw `iv:authTag:ciphertext` OAuth access tokens, refresh tokens, and Facebook Page tokens for all corporate/founder social accounts inside the browser HTML / Next.js RSC Flight payload — which combined with `A20-006` (weak/fallback key derivation) enables offline decryption and full takeover of Al Ramlah's Instagram, Facebook, YouTube, TikTok, and Google Business channels.
- Root cause: `settings/page.tsx` duplicated the `socialIntegrations` SELECT query from `listSocialIntegrationsAction` without reusing its `sanitizeIntegrationMetadata()` projection helper.
- Recommended fix: Apply `sanitizeIntegrationMetadata(row.metadata)` in `app/admin/(dashboard)/settings/page.tsx` before passing `socialRows` to `<ConnectionsSettingsClient />` (or call a shared server-only loader), and store transient OAuth `pendingCandidates` in a short-lived server-only table (`social_oauth_pending_sessions` with 15-minute TTL) rather than a persistent JSONB column on `social_integrations`.
- Test to add: Integration test in `web/tests/settings-secret-masking.test.ts` seeding a `social_integrations` row containing `metadata.encryptedPageAccessToken` and `metadata.pendingCandidates[0].encryptedAccessToken`, rendering/loading `/admin/settings` props, and asserting zero `encrypted*` keys exist anywhere in the serialized client props.
- Effort: S (<2h)
- Confidence: High
- Needs owner decision: no

## Specification: Read-Only Config Health Surface (`/admin/settings?tab=health`)

Per `SWARM_PROMPT.md` §7.A20, below is the exact, zero-secret specification for `/admin/settings?tab=health` to be implemented in Wave 3.

### 1. Access Control, Routing & Zero-Secret Contract
- **Route & Tab**: `/admin/settings?tab=health` (`tab.key = "health"`, label `"Config Health"`, icon `ShieldCheck`), gated on the server by `await requireSuperAdmin()`.
- **Read-Only Guarantee**: Zero write SQL queries (`INSERT`/`UPDATE`/`DELETE`), zero outbound WhatsApp/Social posts, zero secret mutations.
- **Zero-Secret Serialization Invariant**: Neither the SSR loader (`getSystemConfigHealthSnapshot()`) nor the on-demand live probe Server Action (`runSystemConfigLiveProbesAction()`) may ever return raw env values, secret prefixes/suffixes, key lengths, hashes, database DSNs/passwords, R2 access keys, Gotenberg keys, or encrypted/decrypted tokens. Every check emits only typed booleans, enum status codes, integer millisecond latencies, counts of healthy/unhealthy DB rows, and static remediation hints.

### 2. Exact TypeScript Payload Contract (`lib/health/config-health.ts`)


## What Works

1. **WABA Access Token Masking on Initial SSR & Normal Form Renders**: `app/admin/(dashboard)/settings/page.tsx:92-108` omits `whatsappAccounts.encryptedAccessToken` from its SQL `SELECT` projection, and `ConnectionsSettingsClient` (`web/components/admin/hubs/connections-settings-client.tsx:794, 1059, 2365-2367`) initializes `wabaAccessToken` to `""` while placing `"•••••••••••••••• (Encrypted in Neon DB)"` strictly in the HTML `placeholder` attribute rather than `value`, preventing literal bullet characters from overwriting DB tokens.
2. **Social Integration Action-Level Token Stripping**: `listSocialIntegrationsAction` (`web/app/actions/social-scheduler.ts:97-111, 276-295`) omits `encryptedAccessToken` and `encryptedRefreshToken` from its query and strips `encryptedPageAccessToken` and `pendingCandidates` via `sanitizeIntegrationMetadata()` on client refreshes (providing the exact helper needed to fix `settings/page.tsx:75` in `A20-001`).
3. **Public Layout & Legal Page Resilience When `agency_settings` Row Is Absent**: `getCompanyInfo()` (`web/lib/company-info.ts:50-107`) cleanly normalizes Pakistani WhatsApp numbers (`0327...` -> `92327...`) for `PublicHeader`, `PublicFooter`, and `WhatsAppFab`, and gracefully falls back to `DEFAULT_COMPANY_INFO` if `db.query.agencySettings.findFirst()` throws or returns `null` (`app/(public)/layout.tsx:17-25`, `privacy/page.tsx:15-19`, `terms/page.tsx:15-19`).
4. **Super-Admin Enforcement on Catalog Agency Settings & Staff Mutations**: `updateAgencySettings`, `createStaffUser`, `toggleUserActive`, and `updateUserRole` (`web/app/actions/catalog.ts:803, 864, 906, 924`) all call `await requireSuperAdmin()` (`web/lib/auth-guard.ts:39-57`, which re-queries `user.isActive` and `user.role === "super_admin"` live against PostgreSQL) and guard against self-suspension/self-demotion (`userId === currentUser.id` at `catalog.ts:908, 926`).
5. **Gotenberg Health Probe Timeout & API-Key Header Support**: `checkGotenbergHealth` (`web/lib/posters/gotenberg.ts:17-78`) enforces `AbortSignal.timeout(8000)`, attaches `X-Gotenberg-Api-Key` when configured, measures round-trip `latencyMs`, and catches network timeouts cleanly without crashing the caller.
