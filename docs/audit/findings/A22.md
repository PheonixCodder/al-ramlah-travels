## Executive Summary

Inspection of the W0 production build (`web/.next/`) and source tree revealed critical performance, scalability, and serverless deployment blockers across all three pillars:

1. **P0 Rendering & Bandwidth Bomb (`A22-001`):** `public/logo-icon.png` is an unoptimized **`10.64 MB` (`11,153,116 B`, `4096×4096` PNG)** read from disk without caching (`lib/posters/chromium-cdp.ts:32–46`) and base64-encoded into a **`14.18 MB` string**. `lib/posters/render-quotation-pdf.ts:322, 369, 526` interpolates that base64 string **three separate times** into one `index.html`, uploading a **`42.55 MB` (`44.61 MB` UTF-8) multipart payload** to the `1 GB` RAM Gotenberg VM per 3-page quotation PDF and inflating output vector PDFs to `>6 MB`.
2. **Serverless Platform Timeouts & Body Caps (`A22-002`):** Zero routes or pages in `app/**` export `maxDuration`, `next.config.ts` omits `experimental.serverActions.bodySizeLimit` (leaving Next.js 16's **`1 MB` default** on `uploadRawFlyerFileAction`), `/api/uploads/local` hits Vercel's hard **`4.5 MB` request body limit** (plus `EROFS`), and `triggerByIdAndAwaitOrInline` (`trigger/dispatch.ts:275–349`) holds Vercel Serverless Functions open in an `800ms` `sdkRuns.poll` loop for `180s–300s` tasks — guaranteeing `504 FUNCTION_INVOCATION_TIMEOUT` on Vercel Hobby (`10s` default / `60s` max, which also forbids commercial business use) and Vercel Pro (`15s` default without `maxDuration`).
3. **Database & Compute Burn (`A22-003`, `A22-004`, `A22-006`, `A22-007`):**
   - `/admin/desk` 4-second polling (`H5`) fires **2 Server Actions + 5 SQL queries per tick per tab**, including an unconditional `UPDATE whatsapp_conversations SET unread_count = 0, updated_at = NOW()` **write on every 4-second read poll** (`app/actions/whatsapp-crm.ts:519–523`). Meanwhile, two `*/5 * * * *` Trigger crons prevent Neon's `300s` scale-to-zero suspend 24/7 (`730 compute-hours/month`), exhausting Neon Free Tier (`191.9 compute-hours/month`) by **Day 8**.
   - `POST /api/webhooks/whatsapp` executes **`7–12+` sequential network round-trips** per inbound message (`~350–950ms` p50, **`1.2s–2.8s` p95**, violating the `<150ms` target at `route.ts:777`), and scales linearly `O(M)` on batched webhook envelopes.
   - `/admin` Overview (`app/admin/(dashboard)/page.tsx:37–73`) fetches **100% of all historical `applications` + `hotelStays` + `hotels` + `quotes`** into Node RAM without `WHERE` or `LIMIT`, filters `7d/30d/90d` in JavaScript, and serializes all filtered rows **twice** into client props.
   - `db/index.ts:16–20` binds `DATABASE_URL_POOLED || DATABASE_URL` into stateless `neon()` (`drizzle-orm/neon-http` — one HTTPS `fetch` per SQL statement, zero WebSocket `Pool`, zero `db.transaction()` support, extra PgBouncer hop when `-pooler` is passed), while `drizzle.config.ts:9` ignores `DATABASE_URL_POOLED`, and uncached `requireAdmin()` doubles session DB round-trips on every admin page load.
4. **Zero Caching, Bloated Client Bundles & 38-Minute Builds (`A22-005`, `A22-008`, `A22-009`, `A22-010`):**
   - `32 of 36` routes are dynamic (`ƒ`), with **`0`** uses of `revalidate`, `unstable_cache`, or Next 16 `"use cache"`. Public `/` (`force-dynamic`) fires **`13` cold Neon HTTP queries** per pilgrim visit (querying `agency_settings` twice); static legal pages `/privacy` and `/terms` each fire **`2` cold Neon queries**.
   - **`0` uses of `next/dynamic`** exist across all `195` `app/` + `components/` files (`116` marked `"use client"`). Public `/` ships **`1,088.9 KB` (`1.06 MB`)** uncompressed First-Load JS (+ `110.0 KB` polyfills) plus full `SELECT *` catalog tables in RSC Flight payload; `/admin/desk` ships **`1,420.0 KB` (`1.39 MB`)** and `/admin/campaigns` ships **`1,404.6 KB` (`1.37 MB`)**.
   - `npm run build` (`next build --webpack`) took **`38+` minutes** (`15.3m` Webpack compile + `22.2m` / `1.48 GB` `tsc` typecheck over unexcluded `.next`, `tests/`, and `scripts/` + `@vercel/nft` stall before `.next/standalone` was emitted).

## Findings

### A22-001 — 10.64 MB (`4096×4096`) `logo-icon.png` Triple-Embedded as 42.55 MB Base64 HTML Payload on Every Quotation PDF
- Severity: P0
- Category: performance
- Where: `public/logo-icon.png`, `lib/posters/chromium-cdp.ts:32-46`, `lib/posters/render-quotation-pdf.ts:322,369,526,555-564`, `lib/posters/render-multi-package-poster.ts`, `lib/posters/render-single-package-poster.ts`
- Brief claim contradicted (if any): §6.3 / §7 "Luxury 3-page A4 quotation PDF rendered cleanly via Oracle Always Free Gotenberg"
- Evidence: `public/logo-icon.png` on disk is `11,153,116 bytes` (`10.64 MB`, `4096×4096` RGBA PNG). `getCompanyLogoBase64()` (`lib/posters/chromium-cdp.ts:32-46`) calls `readFile(logoIconPath)` on every invocation with zero module-level memoization and base64-encodes the raw file into a `14,870,824`-character (`14.18 MB`) string. `buildLuxuryQuotationHtml()` (`lib/posters/render-quotation-pdf.ts:322, 369, 526`) interpolates `data:image/png;base64,${companyLogoB64}` three separate times (cover logo, header logo, contact card logo) into a single `index.html`, producing a `44,625,000+ byte` (`42.55 MB`) multipart HTTP `POST` body to Gotenberg per quote PDF, and bloating generated vector PDFs (e.g. `public/uploads/r2-local/posters/spotlights/art-am-21d-04_vector.pdf`) to `6,681,134 bytes` (`6.37 MB`).
- Impact (business terms): Sending a `42.55 MB` HTML file over the public internet from Vercel/Trigger to a `1 GB` RAM Oracle Always Free Gotenberg container saturates outbound bandwidth, causes Chromium OOM crashes or `30s+` timeouts during peak quoting, and produces `6+ MB` PDFs that fail slow mobile WhatsApp downloads for Pakistani pilgrims on 3G/4G data.
- Root cause: A raw uncompressed `4096×4096` master design PNG was committed to `public/logo-icon.png` and inlined repeatedly as duplicate `data:` URIs instead of resizing to `256×256` / `512×512` WebP/PNG (`<35 KB`), caching the buffer in memory, and referencing a single multipart companion image file (`files: [{ name: "logo.png" }]` -> `<img src="logo.png">`) or reusable `<svg><symbol>` in Gotenberg.
- Recommended fix: Downscale and losslessly compress `public/logo-icon.png` to `512×512` (`<40 KB`) via `sharp`, memoize `getCompanyLogoBase64()` in module scope, and pass `logo.png` once as an attachment in `renderHtmlViaGotenberg()` (`src="logo.png"`) so the HTML payload drops from `42.55 MB` to `<45 KB` (`~1,000×` smaller).
- Test to add: Unit test in `tests/quotation-pdf.test.ts` asserting `Buffer.byteLength(buildLuxuryQuotationHtml(...), "utf8") < 250_000` and `fs.statSync("public/logo-icon.png").size < 150_000`.
- Effort: S (<2h)
- Confidence: High
- Needs owner decision: no

### A22-002 — Missing `maxDuration`, 1 MB Server Action Body Limit, 4.5 MB Vercel Upload Cap & Synchronous Trigger Polling Timeouts (`H7`)
- Severity: P1
- Category: infra
- Where: `next.config.ts:1-116`, `trigger/dispatch.ts:275-362`, `app/actions/marketing-ops.ts:124-160,1660-1910`, `app/actions/quoting-copilot.ts:83-160`, `app/api/uploads/presign/route.ts:30`, `app/api/uploads/local/route.ts:47-85`
