## 1. Executive Summary

Per Owner Decision **`OD-08`** (`docs/audit/OWNER_DECISIONS.md`), v1 ships with **English UI (`<html lang="en">`) + properly isolated `<ArabicText lang="ar" dir="rtl">`**, targeting Pakistan (`en_PK`) and overseas English/Roman-Urdu speaking Pakistani diaspora (`GB`, `US`, `CA`, `AE`, `SA`), while deferring a full `/ur` RTL Urdu storefront to v2.

Inspecting `app/layout.tsx`, `app/globals.css`, `components/public/arabic-text.tsx`, `lib/constants/brand.ts`, `components/layout/{public-header,public-footer}.tsx`, all public PKR formatting call sites, and heading/section copy across `components/public/**` uncovered **four locale, script, currency, and search-terminology findings**:
1. **Missing `openGraph.locale = "en_PK"` and Pakistan geo/language signals (`S12-001`)**: `app/layout.tsx:64-70` omits `locale: "en_PK"` and `siteName`, causing social and search parsers to treat the site as generic `en_US` rather than a Pakistan-anchored (`PK` / Lahore) travel entity.
2. **Inconsistent Arabic brand name (`الرملة للسفر والسياحة` vs `سفريات الرملة`) & RTL script wrapper hygiene (`S12-002`)**: `PublicHeader` (`public-header.tsx:188, 257`) renders a different Arabic name (`الرملة للسفر والسياحة`) than `BRAND_ARABIC_NAME` (`سفريات الرملة` in `brand.ts:13`, `public-footer.tsx:133`, `voucher/[token]/page.tsx:216`, and Gotenberg PDFs), and dynamic CMS fields lack automatic BiDi isolation if staff paste Arabic/Urdu script.
3. **25+ bare `.toLocaleString()` PKR calls with no locale argument (`S12-003`)**: Calling `amount.toLocaleString()` without `"en-PK"` / `"en-US"` causes Node SSR (`485,000`) vs South-Asian/Arabic browser locales (`4,85,000` or `٤٨٥٬٠٠٠`) to diverge — creating React `#418` hydration mismatch risks and inconsistent PKR formatting across cards, modals, vouchers, and status trackers.
4. **Abstract luxury headings miss high-intent Pakistani pilgrim search vocabulary (`S12-004`)**: Current `<h1>`/`<h2>` copy uses poetic phrasing (`"Sacred Journeys Crafted with Dignity & Comfort"`, `"Sacred Itinerary Architect"`, `"Courtyard Luxury Properties"`) that misses exact commercial phrases Pakistani pilgrims search on Google.com.pk and AI search (`"Umrah packages from Lahore"`, `"Saudi Umrah visa price in Pakistan"`, `"Makkah hotel walking distance to Haram"`, `"Hajj 2027 packages Pakistan Maktab A B C"`).

## 3. Detailed Findings

### S12-001 — Root `openGraph` metadata omits `locale: "en_PK"`, `siteName`, and Pakistan regional targeting signals
- Severity: P2
- Category: seo
- Where: `app/layout.tsx:41-80`
- Brief claim contradicted (if any): None (implements `OD-08` v1 `en_PK` locale posture)
- Evidence: In `app/layout.tsx:64-70`, root `metadata.openGraph` contains only `title`, `description`, `type: "website"`, and `images: [{ url: "/logo.jpg", ... }]`. It omits `locale: "en_PK"` and `siteName: "Al Ramlah Travels"`. Furthermore, neither `app/layout.tsx` nor `app/(public)/page.tsx` sets regional metadata (`alternates.languages` or geo meta tags for Lahore, Punjab, Pakistan), while `OD-08` explicitly selects English UI (`<html lang="en">`) scoped to Pakistan (`en_PK`) for v1 without `/ur` routes.
- Impact (business terms): Without `openGraph.locale = "en_PK"` and consistent entity/canonical signals, WhatsApp link previews, Meta social scrapers, Bing, and regional SERP rankers treat `alramlahtravels.com` as an unlocalized `en_US` document rather than a Pakistan-primary (`google.com.pk`) travel agency, weakening national ranking relevance against `.pk` competitors while risking broken expectations if dead `/ur` hreflang tags were emitted prematurely.
- Root cause: Root metadata in `app/layout.tsx` was minimally configured before Wave 5's `lib/seo/metadata.ts` builder design.
- Recommended fix: In `lib/seo/metadata.ts` and `app/layout.tsx` (owned by `F-SEO-PLAT`):
  1. Keep `<html lang="en">` (`app/layout.tsx:86`) per `OD-08`.
  2. Set `openGraph: { locale: "en_PK", siteName: "Al Ramlah Travels", type: "website", ... }` across all public route metadata builders.
  3. Include self-consistent `alternates: { canonical: routeUrl, languages: { "en-PK": routeUrl, "en": routeUrl, "x-default": routeUrl } }` (strictly pointing to real live English URLs — **never** referencing non-existent `/ur/*` URLs until v2 ships).
- Test to add: Unit test `tests/seo/metadata-locale.test.ts` asserting `buildPageMetadata("/umrah-packages")` sets `openGraph.locale === "en_PK"`, `openGraph.siteName === "Al Ramlah Travels"`, and emits zero `/ur` alternate links.
- Effort: S (<2h)
- Confidence: High
- Needs owner decision: no (resolved by `OD-08`)

### S12-002 — Arabic brand name split (`الرملة للسفر والسياحة` in Header vs `سفريات الرملة` in Brand/Footer/Vouchers) and BiDi script isolation gaps
- Severity: P2
- Category: a11y
- Where: `components/layout/public-header.tsx:188, 257`, `lib/constants/brand.ts:13`, `components/layout/public-footer.tsx:133`, `app/(public)/voucher/[token]/page.tsx:216`, `components/public/arabic-text.tsx:1-29`, `app/globals.css:13`
- Brief claim contradicted (if any): None
- Evidence:
  1. `lib/constants/brand.ts:13` defines `BRAND_ARABIC_NAME = "سفريات الرملة"` ("Safarayat Al Ramlah"), which is used in `PublicFooter` (`public-footer.tsx:133`), digital vouchers (`voucher/[token]/page.tsx:216`), and Gotenberg quotation PDFs (`lib/pdf/render-quotation-pdf.ts:922`). However, `PublicHeader` (`public-header.tsx:188` desktop brand lockup and `L257` mobile drawer lockup) hardcodes a **different** Arabic string: `"الرملة للسفر والسياحة"` ("Al Ramlah for Travel & Tourism")!
  2. `<ArabicText>` (`components/public/arabic-text.tsx:15-28`) properly applies `lang="ar" dir="rtl"` and `font-arabic`, **but** hardcodes `lang="ar"` with no `lang?: "ar" | "ur"` prop, and lacks `unicode-bidi: isolate` (`isolate` / `<bdi>`) protection when rendered inline inside LTR English sentences. Meanwhile, `app/globals.css:13` lists `"Noto Naskh Arabic", "Noto Nastaliq Urdu"` after `var(--font-arabic)` (`Amiri`), and free-text CMS fields (`faqs.answer`, `testimonials.quote`, `heroSlides.subtitle`) render inside LTR `<p>` tags without `dir="auto"` if admins paste Arabic du'as (`ﷺ`, `إن شاء الله`) or Urdu phrases.
- Impact (business terms): Rendering two different Arabic company names between the top Header (`الرملة للسفر والسياحة`) and bottom Footer/Vouchers (`سفريات الرملة`) on the very same page undermines luxury brand polish for Arabic- and Urdu-literate Pakistani pilgrims and creates conflicting entity strings in crawled header/footer chrome. Unisolated inline RTL punctuation in CMS text can also visually scramble adjacent English numbers or parentheses on Safari/mobile browsers.
- Root cause: `PublicHeader` hardcoded an early Arabic translation string instead of importing `BRAND_ARABIC_NAME` from `lib/constants/brand.ts`.
- Recommended fix:
  1. Replace both hardcoded `"الرملة للسفر والسياحة"` strings in `components/layout/public-header.tsx:188, 257` (`F-SEO-SHELL`) with `BRAND_ARABIC_NAME` imported from `lib/constants/brand.ts` (`"سفريات الرملة"`).
  2. Enhance `<ArabicText>` (`components/public/arabic-text.tsx`) to accept an optional `scriptLang?: "ar" | "ur"` (default `"ar"`) and include `[unicode-bidi:isolate]` (`bdi` semantics when inline `as="span"`) so inline Arabic/Urdu phrases never corrupt surrounding English/PKR punctuation.
- Test to add: Component test `tests/seo/arabic-brand-consistency.test.tsx` asserting `PublicHeader` and `PublicFooter` both render `BRAND_ARABIC_NAME` inside `[lang="ar"][dir="rtl"]` elements and zero occurrences of `"الرملة للسفر والسياحة"` remain in `components/`.
- Effort: S (<2h)
- Confidence: High
- Needs owner decision: no

### S12-003 — 25+ locale-unspecified `.toLocaleString()` PKR calls risk SSR/CSR hydration mismatches (`#418`) and inconsistent digit/comma grouping
- Severity: P2
- Category: ux
- Where: `components/public/group-packages-section.tsx:457, 511, 523, 535, 547, 555`, `components/public/group-booking-modal.tsx:306, 451, 490, 518, 535, 552, 569, 764, 766, 771`, `components/public/hajj-inquiry-section.tsx:860, 1226, 1269`, `components/planner/live-summary-card.tsx:333, 337`, `components/planner/steps/review-and-submit-step.tsx:323, 482, 981, 984, 1020`, `components/public/status-tracker.tsx:785, 801, 816, 830, 845, 856, 1028`, `app/(public)/voucher/[token]/page.tsx:196, 201, 202`
- Brief claim contradicted (if any): None
- Evidence: `git grep -n "toLocaleString()" -- app/(public) components/public components/planner` returns **28 bare `.toLocaleString()` calls** with zero locale parameter passed (e.g., `PKR {lowestPrice.toLocaleString()}` at `group-packages-section.tsx:457` and `PKR {totalAmountPkr.toLocaleString()}` at `live-summary-card.tsx:337`). On Vercel's Node 20 runtime (`ICU` default `en-US`), `(485000).toLocaleString()` renders `"485,000"`. On a pilgrim's Android/Windows browser configured to `en-IN` (common across South Asia) it renders `"4,85,000"`, and on GCC diaspora devices set to `ar-SA` it renders Eastern Arabic numerals `"٤٨٥٬٠٠٠"`. Additionally, `hajj-inquiry-section.tsx:857` mixes shorthand `"PKR 2.73M"` with `"PKR 2,725,000"`.
- Impact (business terms):
  1. **React hydration errors (`Error #418`)**: Client components (`GroupPackagesSection`, `HajjInquirySection`, `CustomJourneyBuilder`, `StatusTracker`) re-evaluating bare `.toLocaleString()` during hydration throw console hydration warnings or re-mount flickers for South Asian and GCC diaspora users.
  2. **Financial readability & AI price extraction**: Inconsistent currency strings (`Rs.`, `PKR 2.73M`, `4,85,000`, `485,000`) degrade tabular scannability (`tabular-nums`) and confuse AI price-comparison parsers.
- Root cause: No shared `formatPkr()` currency formatter was established in `components/public/public-utils.ts` or `lib/utils.ts`.
- Recommended fix: Add a deterministic `formatPkr(amountPkr: number, opts?: { includeCurrency?: boolean })` helper using a module-cached `new Intl.NumberFormat("en-US", { maximumFractionDigits: 0 })` (producing identical `"PKR 485,000"` output on both Node SSR and every browser locale worldwide) and pair all PKR price nodes in Wave 6 tables/cards with `tabular-nums`. Replace bare `.toLocaleString()` calls when touching public pricing surfaces.
- Test to add: Unit test `tests/seo/format-pkr.test.ts` verifying `formatPkr(1485000)` deterministically returns `"PKR 1,485,000"` regardless of ambient `LANG` / `Intl` defaults.
- Effort: S (<2h)
- Confidence: High
- Needs owner decision: no

- Where: `app/layout.tsx:44-53`, `components/public/hero-slider.tsx:66-102, 260-310`, `components/public/group-packages-section.tsx:355-375`, `components/public/marketing-sections.tsx:245-395`, `components/planner/custom-journey-builder.tsx:550-575`, `components/public/contact-section.tsx:165-185`

  - Hero fallback `<h1>`: `"Sacred Journeys Crafted with Dignity & Comfort"` (`hero-slider.tsx:69`)

  - Custom Builder `<h2>`: `"Design Your Custom Sacred Journey"` / `"Sacred Itinerary Architect"` (`custom-journey-builder.tsx:558`)
  - Contact `<h2>`: `"Connect with Our Travel Directors"` (`contact-section.tsx:171`)
  Running `git grep -i -E "umrah package(s)? from lahore|umrah visa price|walking distance to haram|masjid al-haram|ladies gate" -- app/(public) components/public` returns **0 heading matches**. Neither city-origin modifiers (`from Lahore`, `from Karachi`, `from Islamabad`), duration modifiers (`10 days`, `14 days`, `15 days`, `21 days`, `Ramadan`), distance modifiers (`walking distance to Haram`, `0 meter Clock Tower`, `Madinah Markaziyah`), nor visa search phrases (`Saudi Umrah visa price in Pakistan`) appear in crawlable headings or `<title>` tags.

- Recommended fix: Pair Al Ramlah's dignified Haramain luxury voice with exact pilgrim search terminology across Wave 6 `lib/seo/metadata.ts` titles/descriptions and spoke `<h1>`/`<h2>` hierarchies (`F-SEO-UMRAH`, `F-SEO-GUIDES`, `F-SEO-TRUST` — see Section 2 Vocabulary Map):

Use authentic Islamic & Pakistani travel terminology naturally in body copy and tables (`Masjid al-Haram`, `Masjid an-Nabawi`, `Markaziyah`, `Maktab A / B / C`, `Ziyarat`, `Meeqat`, `Haramain High-Speed Train`, `LHE / KHI / ISB` departures, `Quad / Triple / Double` sharing in `PKR`) — strictly avoiding unnatural keyword stuffing.
- Test to add: SEO metadata & heading assertion test `tests/seo/search-vocabulary.test.ts` verifying primary hub/spoke `<title>` (`50–60` chars) and `<h1>` tags include target commercial entity terms (`Umrah Packages`, `Lahore` / `[City]`, `Saudi Umrah Visa`, `Makkah` / `Madinah Hotels`, `Hajj 2027`, `Ziyarat`).
